# Reviewed Mac incoming conversations

The Inbox conversation delivery panel inspects one encrypted queued item without revealing or saving its content. The owner selects saved browser access for the current conversation, then separately reviews receiving that item or authenticating a storage receipt for an exact outgoing copy. The review displays the browser identity/fingerprint, conversation, connection, queue identity and action. Receiving a valid answer can resume its exact waiting task; an ordinary message cannot answer a question.

The controller copies the selection into its bounded review and reloads current permission, connection and content status before confirmation. Outgoing receipt reconciliation also checks the saved source text and revision. The authenticated host rechecks cryptographic identity, consent, source/task authority, replay and exact selection through commit. Durable local admission precedes transport acknowledgement. Lost replies require fresh explicit inspection/review; no automatic retry is made. Missing-parent items stay queued with next-item navigation. Focus loss, hidden view, cancellation, selection changes, expiry and clock discontinuities clear or invalidate reviews and suppress late results.

A received message can separately prepare its encrypted storage receipt, then separately review uploading it. Preparation alone sends nothing. Outgoing history distinguishes server storage, recipient storage and task completion; contents/history stay saved until deletion. Reading received text uses the existing guarded Inbox reader. No schema, runtime/model, installed-app, personal-data/key, live-service or Acer news-processing changes.

Validation includes actual authenticated local API/controller tests for unknown queue content, original-copy receipt mismatch, lost acknowledgements before/after server save, reinspection, missing parents, stale copy revisions, changed access/selection, cancellation and a real worker question/answer continuation. Disposable CI runs the shipped React panel in Chromium, Firefox and WebKit, with six scenarios and eleven desktop/phone preview states. Focused browser, visual, full-suite and native acceptance are required before merge; local browser/native automation is not used.
