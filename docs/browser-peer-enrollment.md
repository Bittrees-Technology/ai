# Retained browser peer enrollment

The verified browser host now has a public invitation and peer-review API backed by retained browser keys. This is the storage and host integration for browser-to-Mac pairing. The production recovery page still has no peer-exchange controls: visible fingerprint comparison, reciprocal possession checks, separate task consent and encrypted task/result/approval delivery remain unfinished. No remote-content authority is enabled by this change.

`BrowserKeyLifecycle.invitation` uses its selected retained key and rechecks selection after invitation construction. The existing five-minute public contract binds the remote owner, intended recipient, sender, key epoch and public key. The Mac's existing retained-key modules read the same contract and derive the same full fingerprint. A fingerprint must be compared through an independent trusted channel; accepting the fingerprint supplied alongside an untrusted invitation is not an independent comparison.

`BrowserPeerEnrollment` stores owner-partitioned public pins, bounded retired-key hashes and local-key proofs. Each online operation receives its current key proof from `BrowserKeyHost`, which independently verifies the server registration around the operation and resolves the real retained key. Incoming invitations and stored peer metadata cannot supply identity authority. Host invalidation clears reviews and in-flight scope; no private key handles leave `peerAPI`.

Approval is one-use and bound to the exact original review, full compared fingerprint, owner/recipient, local key selection and peer revision. Wall-clock rollback and monotonic elapsed expiry reject stale reviews. At most four reviews, twenty peer slots and 512 retired-key hashes are retained. Peer replacement advances its epoch and rejects current or retired public-key reuse. Capacity errors never silently discard history. Mac and browser share the pin/state wire schema; Mac storage and behavior remain unchanged.

Browser endpoint database **version3** adds a `peers` store. Final approval checks and writes run in one strict read/write transaction over `slots`, `lifecycle` and `peers`. A different tab cannot revoke or replace the local key between those checks and pin publication. Resolution imports a public key outside transactions and rechecks the peer/local-key proofs afterward. Same-origin code and browser storage remain trusted; these markers do not protect against hostile profile rollback or compromised client code.

Local-key replacement or binding change makes old pins unavailable until an explicit revision-bound reset. Reset retires previous peer keys and clears active pins. Owner-local status/export, revoke and deletion work without an online lease, but do not claim remote revocation. Deletion removes public pin/key history and retains only an owner scope, revision, hashed device anchor and locked marker. A different verified browser registration with an active recovered-or-new key is required to reset that marker. No import restores old peer authority. Complete site-data loss also loses local fences and requires fresh registration/reconciliation outside this module.

The additive version2-to3 upgrade preserves existing lifecycle records, nonextractable handles and encrypted recovery kits. The exact PR149 version2 provider is built from pinned source hashes in disposable CI to verify preservation, aborted-upgrade rollback and refusal to open a newer database. Existing PR143 version1 compatibility tests remain. In-place IndexedDB downgrade is unsupported; the old kit reader can still open separately preserved exported material. No personal browser profile is migrated by the test suite.

Acceptance exercises actual browser IndexedDB/WebCrypto, retained Mac lifecycle/peer modules with encrypted disposable SQLite and simulated native slots, and authenticated encrypted exchanges across browser reload. Additional cases use the actual `BrowserKeyHost` with SIWE, HTTPS, cookies and PostgreSQL registration, including remote revocation, held verification/scope loss and offline maintenance. Public pinning is not reciprocal possession evidence, replay consumption or task consent; the test envelope exchange does not dispatch work. No UI/native/personal/independent cryptographic acceptance is implied.

Mac task schema23, browser ciphertext-outbox schema1 and remote database schema8 are unchanged. No installed app, public service, personal Keychain, model/default or Acer-server news-processing change is included. Mac inference remains independent with no Acer fallback.
