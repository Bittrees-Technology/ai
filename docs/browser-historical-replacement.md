# Browser historical key replacement and recovery

The prior version11 provider creates a real browser key and independently approved conversation. The current provider upgrades its storage, then opens the original encrypted recovery kit. Recovering that material must not make old conversation content eligible for admission.

Two scenarios exercise messages and actual worker questions through explicit browser replacement, peer reset with retired-key rejection, Mac key replacement, both directed peer verifications, and independently renewed conversation consent. New content is accepted once, ordinary replies leave the worker waiting, and an exact answer resumes the existing task once. Reload retains the original outgoing ciphertext and duplicate outcome. Opening the old recovery kit again must neither select its key nor admit old ciphertext; the original kit is retained unchanged.

The browser fixture keeps the synthetic recovery code in page memory only so the test can capture it before reload. It is not a product recovery feature. Chromium, Firefox and WebKit run these scenarios on disposable GitHub runners. The six focused cases precede the full browser suite. No product behavior, schema, UI, installed application, model, personal keys or Acer processing changes are included. Authenticated remote-host and relay recovery acceptance, independent review and personal release acceptance remain separate requirements.
