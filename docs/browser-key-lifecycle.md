# Durable browser key lifecycle

Status: internal coordinator over the [browser key provider](browser-endpoint-keys.md). The synthetic browser fixture exercises it; the production remote page does not mount it. The unmounted [setup/backup controls](browser-key-controls.md) provide reviewed setup and saved-item checks; production verified-client integration, historical restore, pairing, private transport and independent/personal acceptance remain open. This does not activate private remote access. Mac task schema23, browser ciphertext-outbox schema1, installed PR40 and prepared PR142 remain unchanged. Acer news processing and Mac inference remain independent.

## Selection, setup and current identity

The trusted host supplies a fixed local owner, a current verified remote account/device/credential/lease callback, and a separate fresh-registration check. The [browser registration client](browser-device-identity.md) now supplies short-lived server-verified scopes and an explicit fresh-registration observation; actual-browser integration exercises these callbacks, while production host mounting remains open. Neither browser storage, a recovery kit nor a request supplies those authorities. Call `invalidate()` immediately on host identity or permission changes, including logout followed by the same identity. Every operation rechecks current binding and host generation after asynchronous work. No synchronous metadata proof should be treated as permission.

`begin` requires explicit confirmation of the current metadata revision. First setup requires trusted fresh registration and an empty key scope. Replacement retires the old selection immediately and reserves a random new key ID with an epoch greater than every retained slot. Each owner has at most twenty lifetime slots, including retired, interrupted and deleted selections; no silent pruning or ID/epoch reuse occurs. A stale tab cannot replace a newly selected key.

The split `prepareRecovery` and `activatePrepared` operations allow the user to download and reselect the saved encrypted kit before activation. Preparation preserves the preparing metadata revision; activation verifies that exact retained kit as well as its code, identity and key correspondence before publication. The compatible compound `provision` API requires that exact preparing key/revision, explicit confirmation, acknowledgement that recovery was saved, and the separate user-held recovery code. `newBrowserRecoveryCode` produces a random 256-bit code; `browserRecoveryKey` accepts its exact canonical format, not a password or account credential. The provider reserves its generation attempt before cryptography and retains nonextractable handles plus an encrypted kit. The coordinator reopens the saved kit using the supplied code and verifies its full identity/public key before publishing the selection as active. A code acknowledgement is not proof that a human retained a separate copy; the future setup interface must provide and verify that user flow.

Failed metadata publication can resume the same durable material with the correct code. A different code cannot activate a previously saved key. An interrupted attempt without material requires explicit replacement; it never regenerates under the old ID. If activation committed but its acknowledgement was lost, refresh reveals the original active key; replaying an old reviewed revision is rejected.

`resolve` supplies the active runtime pair and a revision-bound proof. `validate` reads current durable selection/slot status and current identity again. Consumers must await fresh resolution and proof validation alongside their own peer/operation permissions before acting, and reject late results on scope changes. Previously returned handles cannot be recalled. Metadata validation is not protection against hostile storage rollback or compromised same-origin code. Full binding equality remains conservative: automatic credential/lease renewal and scoped historical-key use are not implemented.

## Atomic storage and competing tabs

Browser endpoint database **version2** adds one owner-scoped `lifecycle` store alongside the existing `slots`. Selection transitions and slot deletion share strict IndexedDB transactions across both stores. The low-level provider also reads lifecycle metadata in its key transactions; it rejects missing/stale lifecycle revisions, locked scopes and keys other than the selected slot. Raw legacy provider authority cannot bypass an established managed selection. Cross-tab reads recheck the database; no BroadcastChannel notification is relied upon as authorization.

Public lifecycle metadata retains slot IDs, epochs, original bindings, creation times, selected/retired/deleted state and public keys. It contains no recovery code, wrapping key or plaintext private key. Account/device IDs and timing are local metadata, not secret content. Slot records still contain platform key handles and the encrypted recovery kit. Quota/transaction/version-change failures fail closed and preserve previously committed records.

`revoke` retires a key locally while retaining recovery material. `remove` atomically deletes handles, public bytes and the encrypted kit, retaining a deletion marker. These operations require explicit confirmation and the latest revision and remain available after lease expiry. `clear` removes all managed key material and locks the scope in the same transaction. It does not delete ciphertext task history or claim remote revocation. The existing encrypted-kit export remains explicit, owner-scoped and available offline; exported copies survive local deletion.

After clearing or changing the registered device, `reset` requires explicit current-revision confirmation, trusted fresh registration, the same remote owner and a different device ID not present in retained slot history. It preserves monotonically increasing key epochs and retires any previous selection; it does not revive it. Recovering old material does not restore registration, peer pins, grants or replay authority. Complete browser data loss needs external registration/reconciliation, since local markers cannot survive site-data deletion.

## Version1 compatibility and remaining work

Upgrade from the actual PR143 provider preserves existing version1 key handles and encrypted kits without automatically adopting them as active managed selections. Legacy slots remain exportable; initialization with existing uncoordinated slots requires explicit reset under a different freshly registered device. Retained legacy metadata becomes retired history, and the next selected epoch exceeds the prior maximum. Legacy devices may have equal epochs in retired history; new selections cannot reuse them.

The old version1 provider refuses to reopen a version2 database. Its existing encrypted-kit opener still reads the preserved exported kit. Downgrading IndexedDB in place is unsupported; no personal browser database is upgraded by these tests. A separate pinned-source compatibility build verifies the exact PR143 provider and recovery helper hashes. The isolated test module is built for the browser fixture only and never served by the production remote page.

The disposable Chromium/Firefox/WebKit suite covers first registration and confirmation, reload/stable handles, competing replacements, raw-provider bypass denial, failed publication and wrong recovery code, interrupted generation, removal during generation, offline revoke/clear, fresh-device reset, identity/lease/host invalidation, owner isolation, stale revisions/capacity, actual old-version migration/refusal and lost activation acknowledgement. Node tests check recovery-code round trips and metadata invariants. No local browser/native automation, personal key/data access, live service or Acer change is used.

Remaining release work includes native/personal setup and code-retention usability, verified-client mounting, explicit historical recovery/rotation and lease renewal, browser peer review/reciprocal possession, current operation consent and outbox integration, protected client delivery, relay/retention and independent cryptographic review. A recovered key remains material only until those separately authorized lifecycle steps are complete.
