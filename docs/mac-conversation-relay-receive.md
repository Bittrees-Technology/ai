# Explicit Mac conversation relay receipt

The authenticated loopback API can inspect one incoming relay queue item and explicitly admit that exact encrypted item through the existing conversation engine. It has no timer, automatic dispatch, model selection or startup activation. The browser sender and visible incoming controls remain separate integration work.

`POST /v1/private-relay/inspect-conversation` takes `{ connection: { id, expectedRevision }, after, confirmed: true }`. It returns only a transport selection, expiry and page cursor. Inspection does not decrypt the queued envelope, append content, answer a task, reconcile a receipt or acknowledge transport. Relay custody still obtains current identity and native credentials. Page cursors are navigation positions, not durable high-water marks; begin a new pass at `after: null`.

`POST /v1/private-relay/check-conversation` takes the same fields plus the inspected `selection` and one explicit `target`:

- `{ action: "receive", permissionId }` authenticates a message or an exact question answer using current independent conversation consent.
- `{ action: "reconcile", permissionId, id, expectedRevision }` authenticates a recipient-storage receipt for the exact retained outgoing copy.

The selection binds relay message ID, envelope hash, transport revision and storage time. A changed or missing item fails with `CONFLICT` before admission. The target is a selector, not authority: the core engine verifies the envelope, current keys, peer, permission, source access, scope, parent and task revision. A payload for another protocol family cannot be acknowledged through this route. Missing parents remain `PARENT_PENDING`, retain their queue item, and consume no final replay or Inbox outcome. Inspecting the cursor permits explicit navigation to the parent; retrying the original reply later preserves its identity.

The native coordinator holds the existing shared key/peer/permission operation lock before relay custody, and uses custody's bounded identity callback directly. It does not start nested identity operations. Disabled conversation access or relay access denies receipt independently of private-task enablement. Cancellation, expired scope and changed credentials fence admission and acknowledgement. Source and task guards are rechecked by the existing atomic conversation transaction.

Transport acknowledgement happens only after the durable local transaction succeeds. Lost acknowledgement cannot roll back accepted content. If the server has not saved the acknowledgement, rechecking the same original message recovers the retained local duplicate. If the server did save it, inspection may be empty while local history retains the outcome. A reconciled receipt changes the local revision: after an uncertain response, refresh history and explicitly select that current revision before retrying reconciliation. A stale revision remains a conflict. The retry authenticates the original receipt and cannot create a new Inbox item or replace the original ciphertext.

Responses contain metadata and a separate `transportOnly` acknowledgement. Local storage, server transport receipt, browser receipt preparation, task execution and reading remain separate states. Receipt acknowledgement does not upload the Mac's prepared encrypted storage receipt; that remains a separately reviewed outgoing action. Ordinary replies never resume waiting work; exact answers use the existing input-wait transaction, with paused work still governed by its existing state.

Eight focused Node tests exercise real endpoint crypto, retained peer/conversation consent, SQLite reopen, synthetic relay custody/client, authenticated HTTP routes and a real LocalWorker question/answer. They cover acknowledgement loss before/after server persistence, original duplicate recovery, changed selections, reply before parent, receipt reconciliation, tampering, revocation, independent task enablement, concurrent deletion exclusion, identity invalidation during poll/native reads and expiry. The transport and content are synthetic; this is not personal-device or live-server acceptance. No schema or UI changes are introduced. Acer news processing, model/runtime choices, installed apps and personal keys/data remain unchanged.
