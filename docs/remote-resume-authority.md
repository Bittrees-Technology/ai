# Companion resume authority

The companion now has an internal, single-use permission for resuming one paused task at one reviewed revision. Existing status, pause/cancel, template, task-submission and conversation grants do not gain resume authority. This package does not expose a resume endpoint or issue a remote credential.

A local approval records a separate `tasks:resume` identity, owner/device/epoch/permission identifiers, exact task and revision, the locally reviewed model digest, bounded expiry, and an encrypted fingerprint of the task input, source binding and model profile. Replacing an approval revokes the prior one for that device/task. Revoked permission identifiers remain tombstoned and cannot be approved again.

Execution requires a separately authenticated delivery identity and a host-owned access provider. The provider must freshly validate source/dependency rights and the pinned model outside SQLite, then return a bounded synchronous check valid through commit. Omitting the provider denies execution. The core independently rechecks the local task revision, paused state, profile/input/source fingerprint, task deadline, permission identity and expiry. The short command lease cannot exceed five minutes or the permission expiry.

The worker also retains the consumed permission as an execution constraint: before and after every generation (including clarification and multi-part drafts), and before saving completion, it checks the approved digest, exact profile/input/source snapshot and current permission. Model substitution, expiry, revocation and recovery-locked permission deny execution or discard a late result. The constraint survives queueing, clarification waits and restart. Tasks with no remote-resume receipt retain their existing local execution behavior. A new separately reviewed approval is needed to replace this constraint.

The task transition, permission consumption and encrypted idempotency receipt commit in one SQLite transaction. An exact duplicate returns the original receipt without another transition, including after restart. Altered retries conflict. Revocation/expiry prevents remote receipt lookup; the owner can still inspect retained metadata locally. A failed check or receipt write rolls everything back. Resuming an unanswered task puts it back into `awaiting_input`; it does not fabricate an answer or start inference.

Owner-local export includes permission history and receipts. Owner deletion removes both. Permissions are bounded to256 retained identifiers per owner and receipts to1,024; capacity fails closed rather than deleting history. These are pilot bounds, not an automatic retention period. Recovery preserves receipts but locks all resume permissions, including unused permissions. Schema36 prevents earlier writers from bypassing the new retained state.

## Verification

The core scenarios cover separate authority, owner/tenant/identity substitution, missing access provider, concurrent duplicates, altered retries, restart, a real `LocalWorker` with a synthetic runtime, unanswered waits, revocation or task changes during access validation, profile changes, source/model-provider rejection, before/after-transition guard failure, expiry and clock rollback, failed receipt storage, encrypted-state corruption, owner deletion and used/unused backup recovery. The first worker fixture incorrectly opted into model questions while returning an ordinary answer; it was corrected to exercise the intended ordinary-task path. Production behavior was not changed to accommodate that fixture.

An actual compiled schema35 writer at `3dbcf4e02ef22a2f4851779b11ba4255e8f6a4ae` creates the upgrade fixture. Its source archive and compiled store/backup hashes are pinned. Verification checks task and old pause/cancel permission preservation, absence of implicit resume authority, wrong-key rollback, fresh approval and duplicate behavior, older-writer refusal, locked current backup recovery, and rollback using the untouched older encrypted backup. Existing migration checks now expect the current schema36 writer without changing their pinned historical inputs.

## Remaining integration

This is a storage/authority component, not end-to-end remote resume acceptance. The companion now includes `resumeTaskAccess`, combining the existing fresh source/dependency guard with a bounded local model pin and approved-digest/profile comparison. Tests call it through the real resume transaction. No authenticated delivery route or shipped caller is wired yet. Separately consented credential issuance, authenticated encrypted delivery and its replay/queue behavior, reviewed Mac/browser controls, reconnect/offline expiry, old-client compatibility, revocation during delivery and full distributed-client acceptance remain required. A trusted callback is not itself evidence that those integrations work. Existing source access checks are not atomic transactions with a remote source, and a model availability check is not a reservation of future inference capacity.

No permission is activated by installation or migration. The installed application, personal data and keys, Mac model/runtime defaults and Acer news/model jobs remain unchanged.

## Delivery transaction composition (not yet wired to transport)

`executeDelivery` adds a trusted in-process admission boundary for the future encrypted receiver. It requires a synchronous current-authority check and synchronous replay admission/classification. The receiver must finish authenticated decryption before calling it; request data cannot provide these callbacks or authenticated identity.

The authority check runs under the write lock before asynchronous source/model access and again at commit. Replay admission shares the exact transaction with the resumed task, consumed permission and durable receipt. Any thrown error or mismatched new/duplicate classification rolls back all writes. Duplicate receipt lookup also checks current authority under the lock, verifies existing admission, and does not repeat source/model work or the task transition. It cannot retroactively attach a missing delivery record to an earlier plain resume receipt. Accidentally asynchronous checks are rejected.

Five regression tests use a synthetic durable SQLite journal to prove this composition contract, including concurrent duplicate delivery, reopen, permission loss, rollback after journal writes and classification mismatch. This journal is a test fixture, not the shared private replay ledger. These tests do not prove envelope authentication, real private consent, encrypted receipts, transport or worker checks after private key changes. Those integrations remain required; no network route or credential issuer uses this method yet. Existing storage formats and ordinary internal `execute` behavior are retained.
