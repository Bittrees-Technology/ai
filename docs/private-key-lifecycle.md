# Durable Mac endpoint key selection

Status: internal coordinator for the [Mac endpoint key provider](private-endpoint-keys.md). It saves the selected key across restarts, requires reviewed replacement or local revocation, and tracks native cleanup through failure. The [local Mac key controls](mac-private-key-controls.md) now construct it with verified identity for explicitly reviewed setup, and provide offline cleanup. Normal launcher setup stays off; no private content transport is activated. Browser key persistence, endpoint recovery, live pairing and independent/native acceptance remain open. Acer-server's model and news processing stay independent and unchanged.

## Authority and selection

`PrivateKeyLifecycle` receives a local owner, Vault, Store, owner/profile-isolated native entry factory and a callback supplying the current **verified** account/device/credential/lease. Use `endpointKeyOwner(owner)` as the native factory's local-owner value. Stored metadata never supplies registration or consent. Full binding equality is required; automatic lease renewal remains unimplemented.

`begin` requires explicit confirmation and the current metadata revision. It retires the previous selection and reserves a new random key ID with a monotonically increasing key epoch. `provision` creates or reopens exactly that reserved slot through the add-only Keychain provider, then rechecks current authority and metadata before publishing it as active. A lost native-write acknowledgement or failed SQLite publication can retry the same retained key. An interrupted attempt without saved key bytes requires another explicitly reserved slot; it cannot silently generate a replacement under the old ID.

Each owner retains at most twenty lifetime slots, including retired/deleted records. Capacity never silently prunes history or the active selection. Revisions and epochs are bounded safe integers. Replacement immediately disables the old selection; it does not replace trusted peer pins, migrate encrypted history or confirm remote revocation. Local `revoke` retires authority while retaining native bytes. `remove` also commits a cleanup obligation before attempting native deletion. Cleanup remains available after the remote lease expires.

`resolve` returns nonextractable runtime private handles and a metadata proof. A receiver/response host must check `validate(proof)` alongside its separate current peer and operation-consent checks immediately before committing an operation. Host lifecycle changes must also call `invalidate()` immediately to suppress late key output. Reopen and key resolution check native storage; proof validation alone does not detect an external Keychain deletion. Previously returned handles cannot be recalled. Tests connect actual retained-key resolution to peer enrollment and HPKE task admission; this is synthetic integration, not live activation.

## Storage, export, deletion and restore

Task schema **17** adds one owner-scoped `private_key_lifecycle` row. Selected IDs, epochs, bindings, state and pending cleanup IDs are Vault-encrypted with owner-specific associated data. A keyed device anchor and restore lock remain outside the payload. No endpoint private key is stored in SQLite or its backup.

Authenticated local JSON export includes `privateEndpointKeys`: revision, fresh-pairing requirement, retained public slot metadata and pending cleanup count. It contains no private key, pending cleanup ID list or internal anchor. Exporting this metadata does not back up endpoint keys or grant authority.

`Store.deleteAll` locks key authority and replaces metadata with only pending opaque cleanup IDs. Its synchronous transaction cannot delete native key bytes. The authenticated all-data deletion route therefore requires a trusted `privateKeyCleanup` hook when keys or cleanup obligations exist, awaits completion, and verifies completion before deleting task history. A final check under the deletion transaction’s write lock rejects any key selection added by another connection during asynchronous remote-journal cleanup. Missing wiring denies deletion; failed native cleanup returns a fixed error and preserves task history and pending cleanup work for retry. The packaged host now supplies the trusted key controller when its sibling native helper is available, including cleanup while new setup is disabled. `clearAll` supplies the matching internal native cleanup operation; it requires explicit confirmation. Minimal native attempt/deletion markers remain as documented by the provider.

Supported encrypted backup restore locks metadata and advances its revision even when matching Keychain items still exist. Reset requires completed pending cleanup, a different verified device identity and an explicit trusted fresh-registration check. Renewing a credential alone cannot unlock restored/deleted selections. Restored slot history preserves monotonically increasing epochs. Whole-data deletion intentionally removes slot history; a fresh device may begin at epoch one under its new identity. Whole database/Keychain loss, hostile rollback and compromised local code still require external fresh-registration reconciliation.

The existing local-storage recovery kit does **not** back up these endpoint keys. User-held endpoint export/import, lost-device reconciliation, scoped lease renewal, historical-key access, real registration/consent controls and signed native update trust remain separate work.

It also retains the provider's untrusted-reader, immutable-write and HPKE checks.
