# Explicit browser conversation relay sending

`BrowserKeyHost.relayConversationContentAPI.send` uploads one already sealed conversation copy using `{ grantId, id, expectedRevision, confirmed: true }`. Outgoing messages and exact question answers upload their retained original envelope. Incoming messages and questions upload only their retained encrypted storage receipt. Preparing content, opening history, reloading and receiving content never automatically send or retry it. Visible send/review controls and browser relay receipt remain separate integration work.

The host obtains current identity, peer verification and relay sender/recipient registration before committing an attempt. Independent conversation consent, directed keys, replay provenance, exact saved revision and envelope expiry are required. The shared host operation excludes concurrent key, permission and content work. Private-task access does not grant conversation access.

Before network submission, the browser atomically saves an encrypted attempt counter and timestamp beside the retained content. The attempt increases the row revision without replacing ciphertext, consuming a new outgoing sequence or changing incoming replay state. A trusted asynchronous guard rechecks the exact saved row and current permission/key proof before hashing, immediately before upload and before exposing the response. Identity cancellation, deletion, changed content, lost authority or expiry fences the operation. The shared relay client awaits these guards while preserving synchronous guards for Mac callers.

A failed or lost response leaves an uncertain attempt. An explicit retry must refresh the saved revision and uploads the same original ciphertext/message identity. An authenticated server storage observation is retained separately, checked against the original hash and message ID, and cannot move backwards in transport revision or state. Server storage, transport acknowledgement, recipient encrypted storage receipt and task execution are distinct. Only the existing authenticated receipt reconciliation marks an outgoing copy as accepted by its recipient.

`stop` takes the same exact-copy input and works offline within the current local owner profile. It durably stops later uploads while retaining the original and delivery history. It neither withdraws a previously uploaded item nor restores revoked consent. There is no automatic restart. Export and deletion continue through their existing separate operations.

The common browser database advances from version14 to15 so an older strict writer cannot overwrite the new encrypted journal. Existing version14 records remain byte-for-byte intact, report no invented attempts and retain their original ciphertext. The compatibility fixture builds actual pinned version14 providers from commit `6cc6ceb20befbfff95902beae9f9467ae15ea96c` and verifies the source archive SHA before use.

Ten new browser scenarios cover durable retries and monotonic observations, offline stopping, failed-write rollback, actual14→15 preservation/older-writer refusal, lost server response plus reload, incoming receipt-only upload, identity/recipient denial, concurrent work/cancellation, deletion during hashing and an exact answer carried through authenticated Mac HTTP into one real worker continuation. They run in disposable CI browsers against synthetic identities and a real test relay. A Node regression exercises asynchronous relay guards before and after submission. These checks do not establish personal-device or live-server acceptance.

Acer's news model, runtime and briefing jobs remain unchanged. The Mac companion retains its independent literal-loopback model adapter, runtime settings and storage. This package changes no model defaults, installed app, personal keys/data or live services.
