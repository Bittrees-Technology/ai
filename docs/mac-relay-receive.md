# Manual Mac relay task receipt

The companion's authenticated local `POST /v1/private-relay/check-task` route checks at most one encrypted incoming task per explicit request. The body is `{ id, expectedRevision, after, confirmed: true }`, where `id` and `expectedRevision` identify the exact locally active relay credential record and `after` is a relay page cursor or `null`. Start each new pass with `after: null`; a page cursor is not a durable high-water mark. There is no timer, background polling, visible button or startup activation in this change.

The Mac requires both existing private-key/task setup and relay setup flags, a currently paired status identity, a separately active native relay credential, retained verified peer keys and current task consent. The native coordinator acquires key/peer/consent exclusion before relay custody, avoiding nested status-identity operations. Global deletion and concurrent credential/key changes see these operations as busy. Local cancellation/logout invalidates the live identity; a stop, changed credential journal, lost consent, deadline expiry or callback exit prevents further admission or acknowledgement. The metadata-only binding callback closes with custody and never includes its secret.

The relay client validates page bounds, destination, envelope hash and lifetime. The existing task receiver then authenticates/decrypts the envelope and checks retained key/peer/task authority again inside the SQLite admission transaction. Only this durable admission permits transport acknowledgement. Task input uses the model profile previously selected in local consent and carries no sender-selected source, memory, conversation, model or priority authority.

A lost acknowledgement does not undo a committed local task. An explicit retry of the same stored envelope finds the same durable receipt and task. If the server saved its acknowledgement but the response was lost, a later poll may be empty; the original task remains in local task history. Neither outcome automatically creates a browser acceptance/result response, repeats a model run, deletes local history or changes relay retention policy. Invalid or unauthorized ciphertext is left unacknowledged. Remote stop/revocation cannot retract already accepted local work.

The response contains local task IDs and a separate `transportOnly` acknowledgement. Plaintext, endpoint keys, status credentials and relay credentials never cross this new HTTP route. Transport receipt is not task completion or a browser-side acceptance receipt. This package does not implement incoming browser result dispatch or outbound native responses.

Six new engine tests exercise actual retained endpoint crypto/peer/task consent, SQLite reopen and task execution, synthetic distinct native relay slots, the real custody/client/controllers, and the authenticated loopback API. The remote transport is synthetic in these tests: this is not a live-server or packaged personal-device acceptance claim. They cover loss before/after acknowledgement persistence, exact admission deduplication, altered ciphertext, revoked task consent, disabled access, stale revisions, escaped scope, concurrent deletion, stop/expiry during a held key read and origin/authentication denial.

The real-browser transfer scenarios are also wired to the native companion controllers through a closed TLS transport, a disposable PostgreSQL server and separate synthetic native slots. Two additional scenarios cover acknowledgement-response loss after server commit and invalidation during a held poll. Together these are 15 cases across three browsers, including the existing nine strengthened sender cases. They passed focused disposable CI and subsequently passed in the dependent full 1,065-case authenticated return-path run at f26886de3a3c25e79f6cd486fbdd38189ac12904. That full run had no failures, retries or skips. This receiver package still requires its own final-head PR checks after the transfer dependency merges. No new UI is introduced.

Live service policy, final native/browser transport acceptance, visible controls, packaged integration and personal acceptance remain open. No installed app, personal Keychain, live service, Mac model selection or Acer news/runtime/model changes are performed.
