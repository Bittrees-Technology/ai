# Explicit encrypted relay clients

`PrivateRelayClient` performs explicit submit, receipt inspection, bounded polling, acknowledgement and deletion for an already granted browser or Mac endpoint. `PrivateRelayOwnerClient` exports encrypted history and deletes exact records under the owner's browser session without requiring an active endpoint grant. Neither constructor sends traffic, stores credentials, starts timers for polling or processes tasks.

The trusted host supplies the current owner/device/grant context, a scope generation and, only for the Mac, the separate relay credential. Browser requests use the same-origin HttpOnly cookies and account/CSRF headers. Mac requests omit browser credentials and send only the independent relay bearer credential. Both bind every message request to the exact permission ID in `X-Bittrees-Relay-Permission`; the server compares that ID inside its authority transaction. All traffic targets the fixed HTTPS ai.bittrees.org origin with redirects forbidden and caching disabled. The Acer model/news server is not a transport or inference fallback.

Each operation captures a parsed context and validates it again through completion. Owner, device, credential, grant, scope, expiry, wall-clock rollback or monotonic deadline changes reject late results. A host must call `invalidate()` on lock/logout/permission changes; it aborts outstanding fetches and streamed reads. A 15-second request signal also bounds reads. A client permits one operation at a time and never retries automatically. An uncertain write may already have committed: callers must retain original message/revision identities and reconcile through inspection rather than create a replacement operation.

Response bodies must be JSON from the expected URL, without redirects, malformed UTF-8 or oversized declared/streamed content. Receipt responses are bounded to32KiB; paged ciphertext/history responses to2MiB and at most20 records. Errors expose stable generic codes, never raw server bodies or transport error details. Late responses from a transport that ignores cancellation are discarded and their bodies cancelled.

A submission response must identify the exact original message and ciphertext hash. Mutation responses must have valid state/revision transitions. Polling validates owner/recipient routing, message/hash binding, delivery expiry, distinct ordered IDs and exact continuation cursors. It does not decrypt or acknowledge anything. The endpoint remains responsible for current peer/key checks, authenticated decryption, durable replay consumption and independent task consent before processing. Only an explicit later acknowledgement records transport receipt. Poll cursors are traversal positions; restart each poll cycle at null.

Owner export validates ciphertext/hash/routing but preserves expired historical content, has `restoreAuthority:false` and grants no ability to execute or restore permissions. Permission provisioning, native credential custody, browser/native user controls and durable retry scheduling remain separate work. These clients are not yet mounted in the production browser host or Mac app.

Eight engine regressions cover browser/native request modes, exact receipt identity, invalid transitions, response bounds/framing, scope/clock/credential expiry, hung fetch/read cancellation, generic errors and historical export. The real synthetic HTTPS/PostgreSQL suite invokes the clients for maximum-size submission/polling, exact retry/acknowledgement and owner history. Two disposable-browser scenarios exercise actual HTTPS/HttpOnly cookies, browser hashing of maximum ciphertext, reverse messages, stale-permission rejection and cancellation after a held response across Chromium, Firefox and WebKit. Those browser scenarios require GitHub CI; building their fixture locally does not prove they passed. No local GUI automation or personal data is used.
