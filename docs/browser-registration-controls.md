# Browser registration and key setup

Design plan: retain ink #183945, evergreen #28685c, white #ffffff, mist #edf3f6, border #aabec5 and error #8a2630. Use Avenir/system typography, left-aligned text and a 72-character measure. Put the current browser and its expiry above owner-scoped registration history, with one adjacent review surface; place the existing recovery-key controls below. Stack both columns on small screens. Keep keyboard focus visible and actions at least 44 pixels high, with no motion, third-party assets or decorative dashboard counters.

Design review: registration and key setup are separate decisions, so do not imply that registering grants private task permission. Explain replacement and revocation before confirmation. Do not merge registration history with local key history: one is server authority and the other is retained local material. Preserve the established key-backup sequence, including separate code storage and verification of the saved file. Offline cleanup must remain explicit and available after registration expiry.

## Trusted host and explicit setup

`BrowserKeyHost.open` captures one trusted account and session scope. It opens owner-scoped retained key storage, and supplies `mountBrowserSetup` with registration operations and an adapter for the existing recovery controls. The embedding signed-in host must provide authenticated account context and call `invalidate()` immediately on logout, lock or account/session changes, then destroy and reopen for the new context. This module is an exported entry point, not automatically mounted by the production remote page.

Refreshing registration reads the current cookie registration and one server-owned history page. Creation/replacement and revocation have separate exact-target reviews, unchecked acknowledgments, one-use operation IDs and bounded wall/monotonic deadlines. Replacement retires the reviewed registration; revocation stops server verification. Neither action deletes keys, backups or content, grants private-task permission, pairs another endpoint or silently renews a lease. Pagination replaces the current page rather than accumulating an unbounded local history.

The setup host wraps every online key operation in the actual browser client's before/after identity verification. It checks its own generation and trusted account scope before callback entry, and supplies only the current bounded scope to the key lifecycle. It exposes no private key handles. Canceling an idle key review does not erase an acknowledged fresh registration, while cancellation during verification prevents late key setup. Logout/lock invalidation also clears the client's fresh proof. Display hints expire with the observed session and registration leases and cannot authorize an operation by themselves.

A newly replaced registration requires a separate local reset before key setup. The lifecycle status now exposes its selected registration ID without changing storage schemas; the key screen uses this to show reset even when old keys were not deleted. Reset retires old selections and preserves their encrypted backups. New keys still require separately saved recovery code and encrypted kit, re-selection of the saved file, code verification and explicit activation. A wrong activation code leaves the original prepared material resumable; reloading or ordinary sign-in cannot create fresh-registration proof.

Local key history, encrypted export, stop and confirmed deletion remain available within the same trusted local owner scope without network verification. An expired/revoked registration does not silently remove those materials. Failed or lost registration acknowledgments do not auto-retry or supply fresh authority; refresh reconciles metadata, and a fresh explicit replacement is required if initial setup proof was lost. In-flight failures may still represent committed server/local changes, so the interface tells the user to refresh rather than report an unproven rollback.

## Verification and release boundary

The disposable browser suite uses the real shipped view, host, client, HTTPS service, SIWE sessions, PostgreSQL, browser-managed cookies, IndexedDB and WebCrypto. Its closed CONNECT proxy is shared with the earlier identity suite. It never resolves or contacts the public host; the isolated browser context accepts a fixture-only TLS certificate. Scenarios cover the complete saved-backup flow, reload, separate replacement/reset, wrong-code resume, owner isolation, lost/late acknowledgments, scope loss before key creation, expiry/blur, offline cleanup, paginated registration history and keyboard/responsive previews in Chromium/Firefox/WebKit. Browser execution and screenshot inspection take place on disposable CI, not the user's browser.

Production signed-in host mounting, native file-picker and personal acceptance, historical recovery/rotation, reciprocal pairing, private task permission, encrypted transport and independent cryptographic review remain separate requirements. This does not deploy the service or apply a live migration. Mac/content schemas, installed app and prepared archive remain unchanged. The Mac model stays independent, and Acer's model/runtime/news jobs remain unchanged. Relay retention remains an unresolved separate decision.
