# Signed-in browser recovery

Design plan: retain ink #183945, evergreen #28685c, white #ffffff, mist #edf3f6, border #aabec5 and error #8a2630; keep Avenir/system typography and left-aligned text below 72 characters per line. Arrange account access, an explicit browser-recovery entry, then Mac pairing/status controls. Reuse the existing reviewed registration and recovery surfaces with their mobile stacking and visible keyboard focus. Add no third-party assets or motion.

Design review: this page connects a browser to the user's Mac companion, so browser registration, local recovery material and Mac permissions must remain separate choices. Opening recovery controls is explicit; it grants no pairing or task permission. Preserve saved-code, encrypted-backup and verification-before-activation steps. Scope the status renderer to its own buttons so it cannot override recovery requirements. Show a clear path to retry failed loading without implying that missing controls mean keys were deleted.

The actual hosted page now offers an explicit recovery entry after authentication. Its asynchronous host open is bound to the captured account/session scope; scope changes synchronously destroy the old view and reject late opens. Status rendering only changes status-owned buttons. Ordinary blur conceals reviews without replacing authentication; observed session expiry removes the recovery view. Page exit closes hosts and coordination, and a back-forward-cache return reloads before adopting any authority.

`BrowserSessionCoordinator` uses a same-origin Web Lock for authentication/cookie work and a content-free local-storage record with a random current revision and a separate acknowledgment of completed cleanup. Login changes invalidate other current-version tabs; logout publishes its invalidation before waiting for pending authentication. Each authority check reads the current revision, so delayed storage events cannot preserve an old grant. A failed or interrupted login/logout leaves cleanup pending across reload. Missing metadata also requires cleanup; malformed or unavailable metadata fails closed. Cleanup on a mismatched/expired refresh invalidates peers before changing shared cookies. An older completion never rewrites the current revision, so it cannot erase a concurrent sign-out request. No account, key, recovery code, task or message is stored in these coordination records.

A browser without usable Web Locks or local storage must resolve that limitation before signing in. Same-origin scripts are in the trusted client boundary: this marker is not server authority and does not coordinate older clients that do not participate. Online recovery operations still verify the server's current identity before and after use. A wallet prompt that never settles can delay serialized cookie cleanup while local scopes remain invalid. Server lease/revocation, historical recovery, pairing/private task permissions, encrypted task transport and independent review remain separate requirements.

`npm run build:remote` produces `dist/remote-web`; the service must receive that built directory as its asset root. The page uses bundled JavaScript and external CSS under the existing restrictive CSP. Only the index, entry script, settings and bounded hashed JS/CSS asset paths are served; source modules, maps and dotfiles remain unavailable. This change builds the page but does not install or run a public service.

Acceptance uses the actual built HTML/JavaScript/CSS/CSP over the closed disposable CI HTTPS/PostgreSQL service, with actual SIWE, browser cookies, Web Locks, local storage, IndexedDB, WebCrypto and downloads. Cases cover full saved-code/file activation and reload, control isolation, scope loss during verification, durable failed cleanup, peer logout/mismatch, ordered concurrent login, closed-tab verification, denied/corrupt storage, expiry and desktop/phone keyboard previews. Native file pickers, personal data/Keychain and live deployment are not exercised. No installed app, model/default or Acer runtime/news change is included.
