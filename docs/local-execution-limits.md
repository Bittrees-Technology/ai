# Local execution limits

Device exposes machine-local controls for one to four concurrent tasks, a whole-task time limit of 1–1,800 seconds, a minimum-free-memory admission threshold (0 disables it), and pausing new tasks. Initial settings preserve one task at a time and no memory threshold; the whole-task budget is 120 seconds. Model context/output/temperature stay in immutable model profiles. These controls apply only to the Mac companion; Acer's model/runtime/news processing and cloud fallback are unchanged.

Changes require an authenticated, origin-checked local PUT `/v1/device/execution`, strict input, current settings revision and explicit confirmation. GET returns settings plus current local admission state. Settings are stored as version1 `execution-limits.json` in the companion's managed application directory, with private permissions and atomic replacement. The single running companion holds the listening port before opening settings. A malformed/unsupported/symlinked settings file stops startup rather than silently discarding saved limits. Failed writes keep the previous in-memory revision. A lost acknowledgement requires reading current settings; there are no automatic write retries. Settings contain no task content, credentials, hostname or endpoint selectors, and remain outside task/memory exports, deletion and recovery backups. Restoring content therefore does not silently change the machine's scheduling choices. Older app versions ignore this new file and retain their original behavior.

Admission samples OS free memory immediately before claiming each task. Low/unknown memory with a positive threshold keeps work queued without adding an attempt. This is not a memory reservation, resident-memory cap, forecast or guarantee that a model fits; concurrent loading and other applications can consume memory after the sample. It does not change Ollama's own scheduler or affect requests made by other applications. Paused/busy/memory-held queues still run deadline, revoked-template and unsuccessful-dependency maintenance. A sleeping process cannot run timers: expiry is reconciled on its next tick; a fresh source check still precedes writes/results.

A single companion worker owns bounded concurrent slots. Conversations and explicit dependencies retain existing database ordering. Lowering concurrency drains existing work; increasing it admits new eligible conversations. Active task IDs cannot be reclaimed into a second local slot even if a lease expires while a call is still pending. Stop/cancel/source revoke reach the active controllers. The task's limits are snapshotted when claimed and recorded with its model run; changes do not extend an already-running time budget.

The total deadline covers source validation, pinning, memory, all generations and final validation. The worker's Ollama instance permits individual calls up to 30 minutes, while the snapshotted task deadline aborts the entire chain sooner; model discovery outside the worker keeps its existing timeout. At the deadline the task is marked failed with `runtime_limit`, its result is fenced, and no automatic retry is scheduled. A pending non-cooperative call continues occupying its slot until it settles; the companion cannot guarantee immediate memory release or forcibly kill the shared Ollama process. Cancellation cannot undo an already accepted remote action. Run history explains timeout and displays the saved device limits for local tasks; connected-app history retains its existing concealment policy.

Task schema20, browser1 and import1 are unchanged. New model-run snapshots and the `runtime_limit` outcome are additive; no existing task, review, grant or model selection is rewritten. Synthetic engine/HTTP/browser evidence does not establish personal installation, actual model memory capacity, native interaction or live-source acceptance.
