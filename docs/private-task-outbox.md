# Durable private-task sender

Status: internal local R2 backend, not an enabled remote feature. `PrivateTaskOutbox` saves the original encrypted task envelope, returns it for bounded retries and verifies encrypted acceptance receipts. There is no network transport, polling loop, HTTP sending route, startup integration, persisted endpoint key or new UI. This SQLite implementation belongs to the companion; the remote browser still needs its own durable storage adapter and key lifecycle before it can submit tasks. It does not establish completed browser-to-Mac delivery. The Mac companion stays separate from Acer news processing.

## Review, preparation and retries

`enqueue` requires an explicit confirmation, current reviewed peer revision/key epoch, strict source-free task content and a local UUID idempotency key. That local key is hashed for deduplication and is never used as a wire operation/message ID. The module generates wire IDs itself. A trusted synchronous provider supplies current verified account/device binding, local sending-key epoch/key pair and **separate per-peer sending consent** with a revision. Neither a relay nor a request body can provide that authority. The destination still independently checks its own permission to accept tasks.

An immediate SQLite transaction reserves a sequence for the directed endpoint/key-epoch channel and saves an encrypted `preparing` entry. The reservation and sequence increment commit together or both roll back. HPKE runs outside the transaction. A second immediate transaction rechecks identity, consent, key references, peer proof, expiry and entry revision before publishing the resulting envelope as `pending`. No candidate ciphertext is returned before persistence. Concurrent preparation may compute multiple candidates, but only one envelope is committed and exposed; all losers use the committed entry. Future producers sharing this channel must coordinate sequence allocation, including receipt/result producers when implemented.

After interruption, `resume` or the same exact `enqueue` request can finish a `preparing` entry. It never re-encrypts an existing pending envelope. Reusing a local idempotency key with changed content/recipient/review conflicts. Outgoing envelope lifetime is at most 24 hours and no longer than the current verified lease. Expiry, permission/lease/key change, peer revocation or registry revision change prevents new delivery. There is no automatic rebinding, expiry extension or new-operation resubmission. Scoped review/resume across routine identity/permission renewal remains a future integration requirement.

`delivery` checks current state and durably increments a handoff-attempt counter before returning a copy of the original envelope. Call it immediately before transport; `get` and local export are history inspection, not permission to send. A handoff count is not proof of network transmission or receipt. Multiple concurrent handoffs intentionally return identical ciphertext, which the destination's atomic receiver deduplicates. Transport code must not cache a delivery authorization or dispatch from exported history. Bytes already handed to a transport cannot be recalled by later local revocation or stopping.

The outbox allows four asynchronous operations per instance and 256 retained entries per local owner. New work fails at capacity; earlier ciphertext/history is never silently evicted, and exact existing requests remain readable/retriable when otherwise authorized. The content must also fit the codec's 65,536-byte encoded payload limit before any reservation. Each stored entry is bounded to 256 KiB. These are local limits; future network adapters need independent request/rate/body limits.

## Acceptance, stopping and uncertainty

A relay success response or a plaintext receipt cannot mark a task accepted. `acceptReceipt` requires a fresh HPKE Auth envelope from the currently reviewed destination key, with the original operation ID and reversed endpoint/key-epoch routing. Its strict encrypted payload is `{ version: 1, type: "task.accepted", receipt }`. The receipt must match the complete original task header, have a plausible acceptance time within its original admission lifetime and pass all current identity/consent/pin checks again inside the final transaction.

Acceptance is recorded once. Identical receipt content is idempotent even in a freshly encrypted response; a different receipt for the same operation conflicts. Receipt replay can only return the same already recorded acceptance state and never dispatches work. The original task ciphertext remains unchanged. A fresh response can reconcile an earlier acceptance after the task envelope expires, provided the original binding, permission and pins are still valid. This receipt is **accepted into the destination's queue**, not running, completed, read or externally published.

`stop` is an explicit local revision-checked operation available without a current remote lease. It prevents further local retries and does not cancel or retract a destination task. A valid late encrypted receipt still records actual acceptance after stopping. If receipt verification fails because of revocation, expiry or changed identity, the outcome remains uncertain; failure does not prove that the destination did not accept the task. Creating a new operation requires a fresh user decision and can create a second task if the first was already accepted. No automatic uncertain-outcome retry under a new ID is implemented.

The destination's durable receipt producer/outbox and live receipt transport are still open. Tests create the response with the actual envelope codec around the real receiver's receipt; this verifies the sender's authentication/association checks, not a deployed bidirectional service. No result viewing or exact-action approval transport is enabled.

## Storage, restoration and local controls

Task schema **15** adds owner-scoped outbox rows and keyed channel counters. Content, original ciphertext, permission metadata and receipt evidence are Vault-encrypted with owner/entry-specific associated data. Indexes contain opaque local IDs and keyed client/operation/channel hashes. The module stores no endpoint private key. Local history remains until confirmed data deletion; authenticated local JSON export includes `privateTaskOutbox`, which is private content and never a remote-status projection.

Supported task/coordinated restore preserves the history but independently locks every outbox row and advances its revision. Restored entries cannot be resumed, delivered or marked accepted; they remain inspectable. The existing peer-registry restore lock also requires a fresh local device identity and key reviews. New pairing does not automatically unlock old outgoing operations. Confirmed whole-data deletion removes outbox rows and channel counters with task history and locks peer trust. External exports/backups or envelopes previously handed to a relay are independent copies. Hostile filesystem rollback and compromised endpoints are outside these guarantees.

Older engines cannot open schema15. Rollback requires the original compatible backup restored separately. The [synthetic compatibility receipt](evidence/private-outbox-schema-compatibility-2026-09-23.json) verifies the actual prepared PR104 schema12 engine's task preservation through current15, older-engine refusal and restoration of its original backup. The reproducible check is `scripts/check-private-peer-upgrade.mjs` with the reviewed `BITTREES_OLD_APP_RESOURCES`, after building current source. Tests separately migrate schema14 tasks and receipts to15. Neither the installed PR40 app nor prepared PR104 archive is replaced.

## Verification and remaining gates

Tests connect two disposable stores with reciprocally reviewed public keys, send real HPKE task envelopes through the atomic receiver, lose the initial response, reopen the sender database, resend identical ciphertext and reconcile an authenticated acceptance. Additional tests cover concurrent producers/sequence allocation, interrupted/failed preparation, changed-content retries, confirmation/review denial, late consent loss/revocation, stop/receipt races, wrong or conflicting receipts, expiry, owner isolation, capacity, restore/deletion, schema migration and local HTTP export. Keys and authority are injected test fixtures; these checks do not prove persistent key recovery, process-level native acceptance or human fingerprint comparison.

Remaining: browser-side durable sending storage, actual endpoint secrets and user-held recovery, reciprocal pairing and consent UI, scoped resume, receipt/result producer outboxes, durable ciphertext relay/transport, encrypted conversation replies/results/exact approvals, real offline UX, client/update trust, native/browser acceptance and independent review. Relay ciphertext retention and operational metadata retention remain unanswered, separate choices. This local outbox does not settle either policy or enable uploads.
