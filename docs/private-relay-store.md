# Private relay ciphertext repository

`RemotePrivateRelayStore` is an inactive PostgreSQL repository, added by migration010. Production startup, HTTP routes, browser/Mac transport loops and cleanup scheduling do not import or activate it. Its required policy has no retention defaults. The Acer model and news-briefing path are unrelated and unchanged.

A current SIWE session and browser registration plus an independently enabled relay grant authorize browser operations. The Mac uses its distinct private-relay credential. Submissions require both endpoint registrations and relay grants to remain current through commit; both must belong to the same owner and have opposite endpoint kinds. Session, registration, grant and message-expiry deadlines are checked within the transaction. Per-owner locks serialize writes, quota checks and maintenance. New grant IDs never inherit prior queues.

Only the authenticated encrypted envelope, its domain-separated hash, routing/epoch/sequence fields and transport bookkeeping are stored. The relay has no private encryption keys or plaintext. It checks framing, routing and size; the destination still must authenticate/decrypt, validate current keys and consume replay identity durably before processing anything. A storage receipt is not task acceptance. A destination acknowledgement asserts durable transport receipt, not model success or approval. The future endpoint client must send it only after its own durable acceptance or rejection. Receipt acknowledgement can occur after envelope expiry for a previously downloaded message; it grants no new delivery or task authority.

Exact repeated submissions return the current receipt, including a deleted tombstone, without replacing or resurrecting content. Changed content under the same message ID and sequence collisions conflict. Concurrent retries produce one record. An expired envelope cannot be resubmitted; authenticated inspection reconciles its receipt instead. Inspection, acknowledgements and endpoint deletion require the original grant identity. Acknowledgement and deletion bind the exact revision, and acknowledgements also bind the envelope hash. Repeating the same successful acknowledgement/deletion is idempotent; an old acknowledgement may report a subsequent deletion.

Polling returns bounded pages of unreceived, unexpired messages addressed to the current recipient grant and sent under a still-current sender registration/grant. It does not acknowledge or remove anything. The stored envelope hash and byte length are checked before ciphertext is returned. Cursors order a single traversal by storage time and message ID; they are not durable change-feed offsets. Restart each poll cycle at a null cursor so concurrently inserted messages with earlier timestamps/UUIDs cannot be missed. Revocation cannot retract a payload already downloaded.

An authenticated owner can export retained encrypted history and delete exact records even after endpoint grants expire or are revoked. Exports contain no keys or credentials and explicitly confer no restore authority. Export is paged, not a transactionally frozen snapshot across multiple calls. Plaintext export and task history remain endpoint responsibilities.

Each message snapshots the explicitly supplied policy. `until-deleted` retains content after receipt or envelope expiry until deletion. `delete-after-receipt` clears ciphertext on acknowledgement. A separately selected bounded unreceived policy hides expired pending content immediately and allows internal cleanup to clear it; an `until-deleted` unreceived policy does not. Delivery validity and storage retention are independent. No live choice is made here.

Deleted content leaves a tombstone until the later of deletion time and original envelope expiry, plus the chosen seven- or thirty-day metadata interval. This prevents cleanup from enabling replays of an otherwise valid original envelope. Retained content keeps its necessary routing metadata; this is not an implementation of general operational-log retention. Cleanup processes at most the requested bounded number of records and skips busy owners. A caller must schedule further passes; no timer runs here. Backup deletion requires the future host's explicit backup policy.

Owner row quotas include tombstones, while byte quotas count retained serialized submission bytes. Deletion frees content bytes but a tombstone continues consuming a row until cleanup. This deliberately prevents retries from bypassing bounded metadata capacity. Limits apply atomically under concurrent submissions. Policy changes affect newly stored messages, not historical retention promises.

The actual PostgreSQL integration suite covers real SIWE/device pairing and separate relay grants, maximum-size authenticated HPKE round-trip after repository reopen, concurrent exact retries/conflicts, bidirectional pagination, scope/owner isolation, receipts/deletion, grant replacement, sender revocation, corruption, row/byte quotas, SQL rollback after envelope/grant expiry and clock rollback, receipt retention snapshots, busy-owner cleanup and tombstone expiry. All fixtures use isolated synthetic accounts. Live hosting, HTTP/CSRF controls, automatic endpoint delivery, independent acceptance and retention decisions remain open.
