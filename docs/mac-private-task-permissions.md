# Mac private-task permission controls

Connections now mounts **Private task permissions** alongside key and peer review. Authenticated local status/review/confirm routes connect `CompanionPrivateTaskPermissions` to the persisted consent layer and real `RemoteClient` verified identity scopes. Every permission checkbox starts off; neither a saved key nor a reviewed peer silently enables tasks, receipts or results. New setup remains off in the normal launcher. No task listener, private transport, background work, personal permission or hosted service is activated.

## Exact review and confirmation

The form selects one reviewed peer, separate incoming/outgoing text-task and receipt/result choices, an explicit local model for incoming tasks, and 15 minutes or one hour. Receipts require incoming tasks; results require receipts because the result includes its original admission receipt. Turning off a prerequisite clears its dependent choices. No checkbox is automatically turned on. The server computes expiry from the selected duration, capped by the verified paired-device lease; the review displays the exact expiry.

Preparation accepts strict choices plus expected consent/key/peer revisions. Under a fresh verified identity scope it resolves actual retained-key and peer proofs and captures the consent module’s original review, full binding and model hash. The user sees account, this Mac, other device, reviewed fingerprint, selected model, all four on/off decisions and expiry. The preview is a clone, not mutable authority. Only a one-use review ID and explicit confirmation/acknowledgement are accepted at confirmation.

Confirmation obtains a new verified identity scope, checks the exact same full binding and revisions, and prepares the original captured choices without recalculating or extending their expiry. New key/peer proofs and model configuration must match the reviewed ones. An outer SQLite immediate transaction checks the original UI-review deadline after acquiring the write lock; the consent module’s nested approval independently rechecks proof/model/permission state before publication. A wait for the database cannot extend the review deadline. No remote owner, profile substitution or extra request authority is accepted.

Status reads only local metadata, never native secret bytes or the remote service. It labels choices as saved with the connection unchecked, rather than implying currently authorized delivery. Revoked, expired and locally stale/restored choices are distinguished. A change to identity not visible in local metadata is caught by the next verified operation. Metadata status does not replace current identity verification.

## Revocation, privacy and uncertain outcomes

Revocation has a separate five-minute review and acknowledgement and works offline for the fixed local owner, including while new setup is disabled. The same final deadline check and consent revision check apply. It prevents future admission and further local sending under that grant; it does not silently cancel already accepted local tasks, erase their history or retract previously emitted/exported copies. The UI explains these limits. New result consent cannot release tasks admitted under an older grant.

Key, peer and permission work share the parent’s operation lock. Starting one kind of review invalidates pending reviews of the other kinds. Logout invalidates pending permission review and the active verified identity scope. All-data deletion rejects active permission work, invalidates pending review, performs existing native-key cleanup and clears encrypted permission content. Failed or uncertain confirmation is never automatically retried. Refresh shows durable local state before another explicit review.

Focus loss, page hiding, Escape, cancellation, form changes and review expiry clear the visible review and acknowledgement. Focus loss/cancellation also reset the form to all permissions off. Generation checks suppress late review and confirmation output after hiding. Already confirmed work may have completed before a view was hidden; hiding is not represented as cancellation. Changing a prerequisite clears dependent permissions, and a successful save returns the form to all off.

## Verification and limits

Controller tests use the actual verified client, key/peer/consent modules and authenticated local routes with synthetic native entries and remote identity transport. They verify one-use acknowledgement, cloned preview tampering, unchanged exact choices and capped expiry, fresh confirmation identity, altered keys/peers/model, expiry, revoked registration, offline revocation, mutual review invalidation, busy all-data deletion, logout invalidation during native reads, deletion cleanup and the deadline crossing while acquiring the publication lock. UI-controller tests cover all-off defaults, captured revisions, acknowledgement, expiry, hidden delayed review and no uncertain retry.

Disposable GitHub browser tests render the actual React panel with synthetic API replies in Chromium, Firefox and WebKit. They cover independent choices, dependency clearing, exact summary/acknowledgement, revocation wording, late-response hiding, no retry, keyboard confirmation and desktop/mobile form/review layout. Preview artifacts are reviewed before merge. The existing Avenir/system, ink/mist/evergreen palette and left-aligned layout are retained, with compact checkboxes, visible keyboard focus and minimum44px controls. No local browser automation is used.

Task schema18/browser schema1 are unchanged. [Mac local dispatch](mac-private-task-dispatch.md) now uses these permission providers under a separate off-by-default gate. Live relay transport remains unwired. Reciprocal possession, browser endpoint keys, user-held endpoint recovery, fresh registration after restore, scoped reconnect/resume, encrypted replies/approvals, hosted operations and independent/personal acceptance remain open. Installed PR40/prepared PR104, personal data/Keychain, model settings and Acer-server model/runtime/news jobs remain unchanged; the Mac companion stays independent.
