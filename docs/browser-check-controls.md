# Browser device check controls

The signed-in recovery page mounts explicit device-check controls after registration, key recovery and reviewed device identities. Both endpoints must have reviewed the other's public invitation first. The browser uses the retained `BrowserKeyHost.checkAPI`; no production test hooks, key export or automatic message delivery are added.

Choose a reviewed Mac, review the exact device and confirm an unchecked acknowledgment to create a challenge. Copy or download the encrypted message and take it to the Mac's device-check controls. Paste its encrypted reply into the browser, review the route and choose **Verify and save Mac reply**. Separately, answer a challenge started on the Mac and take that answer back there. Answering alone records no completed browser proof; each endpoint completes its own challenge. Neither action grants task permission.

Saved history distinguishes preparation, pending challenge, answer, expiration, stopped and verified records. Reopening a saved message uses the original encrypted preparation/ciphertext and sequence. History export contains only the typed metadata summary, without preparation keys, nonces or encrypted messages; it is not a restorable grant. A recorded verification is history, not current server access, reciprocal completion or a live connection. Future task transport must independently validate current keys, pins, proof and separately reviewed permission in its own transaction.

Every action starts with an original key, peer and check-history snapshot. Submission rechecks those snapshots; the durable provider remains the authority and revalidates changes atomically. Registration, key or peer controls cancel stale check reviews through the shared host generation. Account changes, blur, hidden documents, Escape, two-minute review/response limits, wall-clock rollback and monotonic deadlines discard transient reviews and outputs. Passive stale-view cleanup does not cancel newer work in another panel; blur does not reset resumable key recovery. Confirmation is never carried into another action.

A server verification failure may follow a local commit. The UI discards the old review, disables dependent actions and requires a refresh to inspect history. It never silently retries a mutation. Offline stop and history deletion are separately reviewed and affect this browser only. Deletion removes check records and their encrypted preparation material, retains minimal hashed device/shared sequence markers, and requires a different registered browser identity with an active key before reset. Reset does not restore old proof. Peer-list resets retire old Mac public keys, so fresh reciprocal pairing may require a new Mac key. Historical rotation/recovery remains separate work.

Validation uses the actual built HTML/JS/CSS/CSP, real signed SIWE sessions/cookies, isolated HTTPS/PostgreSQL, retained browser keys and real Mac lifecycle/peer/check providers with disposable encrypted SQLite and simulated native slots. Browser tests run only on disposable GitHub runners. Personal browsers, Keychain, installed Mac app, Acer runtime/models/news jobs and live hosted service are unchanged. Manual device-check UI does not complete browser task consent, private task/result/approval transport, personal/native release acceptance or deployment.
