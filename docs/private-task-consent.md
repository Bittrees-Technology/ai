# Persisted private-task consent

`PrivateTaskConsent` supplies the missing durable local permission layer for the private task receiver, sender and response producer. It connects actual endpoint-key and peer-registry proofs to explicit, expiring per-peer choices. [Mac permission controls](mac-private-task-permissions.md) now connect its reviews to authenticated local routes and fresh verified-device scopes. There is still no startup task dispatcher, hosted service or automatic grant. The existing authenticated content export includes the saved decisions. Installed PR40, prepared PR104, personal Keychain/data, model defaults and Acer news processing are unchanged.

## Independent choices and review

A strict review request contains the expected consent revision, exact peer/key epoch, expiry and separate booleans for receiving tasks, sending tasks, sending acceptance receipts and sharing results. Receiving requires an explicitly selected immutable local Ollama profile; sending alone carries no local model selection. Receipt sharing requires receiving, and result sharing requires receipt sharing because each result carries its admission receipt. None defaults to true. A grant lasts at most 24 hours and cannot exceed the current paired-device lease. Source access, memory, tools, approvals, remote-selected models and arbitrary extra fields are not accepted.

Preparation resolves the actual retained Mac key and reviewed peer key under the host’s trusted current identity provider. The review captures full identity, selected-key and peer-registry proofs, exact profile configuration hash, original choices and the consent revision. It expires within five minutes and returns a clone. Approval consumes the review, requires explicit confirmation and acknowledgement, then checks all proofs, current identity, profile and revision under a SQLite immediate transaction before publishing the grant. Returning a modified preview cannot substitute authority. Invalidation clears pending reviews, including those still waiting on native key reads; it does not itself revoke a saved permission.

The host must supply fresh verified identity, not saved registration metadata, and must renew that short scope separately for review and confirmation. A future mounted controller must also make the independent choices clear, clear hidden/changed reviews, and coordinate logout/credential invalidation. The mounted Mac controller supplies separate fresh scopes for review and confirmation; live dispatch remains unwired. A public-key pin or pairing credential alone never creates task permission.

## Use and revocation

`resolve(peerId)` reopens the retained key once and returns `receive`, `send` and `respond` callbacks for the existing protocol modules. Each callback rereads saved consent and revalidates current identity, selected key, peer proof, expiry and profile configuration. CryptoKey handles remain stable during an operation, allowing existing post-cryptography and transaction checks to compare them. Returned binding and pair containers cannot mutate the retained authority. Providers return null for another peer or a choice that was not approved.

The host must pass these callbacks directly and keep its verified identity scope valid through the protocol’s final check; it must not cache a previously returned authority object for later operations. Identity still has the existing bounded freshness window. External Keychain deletion is observed when reopening the key; metadata proof checks do not instantly detect a separate process deleting native bytes after resolution. Normal key cleanup changes metadata first and fences existing providers.

Revocation is explicit, revision-bound, offline and does not require a live remote lease. Replacing permission invalidates earlier providers, unsent tasks and responses that captured the old grant. Receipt/result production must match the exact admission grant revision: enabling result sharing later cannot release previously accepted tasks. A fresh permission applies to newly admitted tasks. A changed peer-registry revision conservatively requires fresh permission review, even if another peer changed.

Revocation prevents new admission and further local encrypted sending under that permission. It does not cancel an already accepted local task or delete its history; those use existing explicit local cancel/delete controls. It cannot retract already delivered bytes or exports. Model outputs remain unreviewed drafts. No source, tool, memory or publication permission is added.

## Encrypted persistence and restore

Task schema18 adds one owner-scoped `private_task_consents` row containing a monotonic revision, restore flag and Vault-encrypted grant array. Public identities, key proofs, choices and model references are encrypted with owner-bound associated data. The array holds at most 20 peer slots and 128 KiB of ciphertext; revocation retains the current revoked record. Replacement overwrites that peer’s prior choices at a higher revision; this is current permission state, not a full audit history. A replacement for an existing peer uses the next owner revision. Capacity or malformed storage fails closed.

Supported backup restoration advances the consent revision and sets its restore flag, as well as the existing key/peer restore locks. Old permission callbacks and pending reviews cannot resume. A new explicit grant requires freshly valid key and peer proofs; clearing the consent restore flag marks every other old grant revoked. There is no reset/recovery bypass here. Confirmed whole-data deletion clears the payload and preserves only owner identifiers, the advanced revision and a lock flag to prevent stale-review reuse. It removes no independent backup/export copy.

Schema17 tasks migrate intact with no newly granted consent. Engines supporting schema17 or older must refuse schema18; rollback uses the original compatible backup restored separately. The [compatibility receipt](evidence/private-task-consent-schema-compatibility-2026-09-23.json) records an actual signed PR104 schema12 bundle preserving a synthetic task through the current upgrade, refusing the newer database, and restoring its original backup separately. This is not personal upgrade or native acceptance.
