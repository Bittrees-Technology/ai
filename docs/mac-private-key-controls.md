# Mac device-key controls

The Connections dashboard now has **This Mac’s private key** controls backed by the authenticated loopback API and `CompanionPrivateKeys`. This connects retained-key storage to reviewed user actions and the all-data deletion path. It does not enable browser pairing, private task transport or recovery. Installed PR40, prepared PR104, personal Keychain/data, model settings and Acer-server news processing remain unchanged.

## Setup and review

Construction, local status refresh and viewing saved metadata do not generate keys or contact the remote service. The packaged engine constructs the controller only when its sibling `PrivateKeyInstall` helper is present. New setup additionally requires an explicitly enabled remote client and `BITTREES_PRIVATE_KEYS=1`. These are development options for the packaged engine; the normal native launcher does not inherit them and keeps setup off. This change does not enable either option on a personal installation. Offline removal and data-deletion cleanup remain wired when the helper is present even if new setup is disabled.

`GET /v1/private-keys` returns availability and local public-key lifecycle metadata. A saved key is labeled **Device key saved**, never a verified current connection. `POST /v1/private-keys/review` accepts a strict action, expected metadata revision and, where required, key ID. Create/replace/resume reviews obtain the exact current paired account/device through `withVerifiedDevice`; revoke/remove/cleanup reviews work offline for the fixed local owner. A single pending review expires within five minutes/the remote lease. Preparing a review performs no key mutation.

`POST /v1/private-keys/confirm` requires the one-use review ID, `confirmed:true` and `acknowledged:true`. The controller consumes the review before work, checks expiry and exact revision, and re-verifies the same remote binding for create/replace/resume. Confirmation fields cannot substitute an action, key, account or device. New setup reserves a fresh slot and provisions it; an interrupted native write leaves the durable preparing slot for **Finish key setup**. That action attempts the original retained key, never silent regeneration. Missing interrupted keys require reviewed replacement. Replacement retires the old selection and retains its bytes until separately removed. Local disable does not claim remote revocation.

The review explains key loss, replacement and current recovery limits. The storage recovery kit does not back up endpoint keys. Fresh-registration reset after restored/deleted key metadata remains unavailable here and fails closed. Browser keys, reciprocal fingerprint comparison, user-held endpoint recovery and complete peer rotation remain open.

## Deletion and lifecycle

Removal commits a cleanup obligation before native deletion; failures remain visible and retryable. The data-deletion screen explicitly names device keys and warns about unreadable encrypted history and the storage recovery kit’s limits. All-data deletion rejects concurrent key operations, invalidates pending reviews even when no key exists, then invokes the controller's cleanup before deleting task history. Failed cleanup preserves history and reports a fixed error. A final transaction check still rejects keys selected during asynchronous remote journal cleanup. If the helper/controller is unavailable and keys remain, deletion fails rather than falsely reporting successful key removal.

Dashboard logout clears pending key review and invalidates an active identity scope. Late key completion cannot publish an active selection after invalidation, although retained bytes/preparing metadata may remain for later explicit resume or cleanup. Focus loss, page hiding, Escape, refresh and cancellation clear visible reviews and acknowledgements. UI generation checks prevent late responses from reopening reviews or notices. Already confirmed work is not automatically retried or represented as cancelled solely because the view was hidden.

## UI and verification

The panel uses the existing Avenir/system typography, ink `#183945`, mist `#edf3f6`, white, evergreen `#28685c` and blue focus `#29658b`. A single left-aligned panel separates saved status, individual key actions and an inset review. It uses no external fonts/assets, displays no private key bytes, wraps account/device identifiers and retains visible keyboard focus and minimum 44px buttons.

Engine tests exercise actual controllers, the key lifecycle, verified remote client, native-slot substitutes and authenticated local routes: explicit acknowledgement, one-use review, current revision/identity, mutation of returned review, uncertain native writes/exact resume, replacement, offline revoke/deletion, cleanup failure, restore locks, busy deletion, logout during creation, review invalidation during empty-data deletion, UI expiry and late-response fencing. Browser tests render the actual React component with synthetic API responses in Chromium, Firefox and WebKit and cover confirmation, deletion wording, stale/late responses, keyboard dismissal and desktop/mobile layout. These UI fixtures do not claim live service or Keychain behavior; those boundaries have separate engine/service/packaged-native tests.

No local browser automation is performed. Personal native acceptance, signed update/access trust, a hosted identity service, real reciprocal pairing/consent, endpoint recovery and private message delivery remain release work. Mac task schema17 and browser database version1 are unchanged.
