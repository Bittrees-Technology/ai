# Retained browser task permissions

`BrowserTaskConsent` implements explicit permission for one reviewed Mac: sending source-free query, summarize and draft tasks, and separately reading returned results. The browser cannot choose the Mac model, memories, source access, tools or publication authority. The Mac independently approves receiving tasks, its local model profile and returning receipts/results. This module adds no Acer-server route or fallback.

A review captures the actual retained browser key, reviewed peer and independently completed browser challenge. Approval requires that original one-use review, an explicit acknowledgement, the expected permission revision and unchanged authority. Reviews expire within two minutes; grants expire within one day or the current device lease, whichever is earlier. These are authorization deadlines, not automatic content deletion.

Choices are saved under a nonextractable AES-256-GCM CryptoKey in IndexedDB with a random 96-bit IV and identity/revision-bound authenticated data. At most20 peer grants and32 local owners are retained. Capacity does not prune existing history. The browser profile and same-origin code remain trusted; local encryption is not hardware-backed protection, backup authority or protection against hostile profile rollback. Temporary owned plaintext buffers are wiped where possible; JavaScript strings and runtime copies cannot be reliably erased.

## Authoritative task operations

The internal `authorize` method resolves actual retained key handles and builds an operation-scoped guarded outbox. Every outbox transaction reads the current key lifecycle/slot, peer pin, completed check and encrypted permission row in that same transaction. Revocation in another tab cannot race a later publication or result release through a cached permission callback. Generation, wall-clock rollback, monotonic deadlines, current binding and grant expiry are also checked. The trusted caller must maintain a freshly verified identity scope throughout each operation; returned providers expire within two minutes and must not be reused as a long-lived session.

The [task composition backend](browser-task-composition.md) encrypts the exact reviewed input locally, then atomically retains that preparation with its original operation, deadline and shared sender sequence. It seals with retained endpoint keys and returns ciphertext only after guarded publication. An interrupted reservation can be explicitly resumed from its saved input. Exact committed ciphertext is reused; it is never regenerated for a retry. Browser revocation cannot retract previously copied ciphertext; receipt still depends on current independent Mac permission and the wire deadline. A new random permission ID accompanies every approval, so deleting a permission row and granting revision1 again cannot authorize older task ciphertext. Legacy rows without a permission ID remain exportable history but cannot be delivered or opened under a new grant.

The verified host exposes permission status, prepare, approve, revoke, clear and reset. Online changes use fresh server identity before and after the operation. A lost final verification may follow a committed local write: inspect fresh status instead of automatically replaying the approval. Offline owner-local revocation and deletion require exact revisions. Deletion removes the permission ciphertext/key and retains a minimal locked marker. Reset requires a different verified browser device identity and starts with no grants.

## Compatibility and verification

Previous keys, checks, shared sequence counters and exact task ciphertext are preserved; the upgrade grants no permissions. The worker output and native key slots are synthetic: no local model or personal Keychain is used. Verified-host cases use the actual SIWE/HTTPS/cookie/PostgreSQL path. Local evidence records the completed test results.
