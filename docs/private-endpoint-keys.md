# Mac private endpoint key storage

Status: internal retained-key provider and packaged native helper. The [local Mac key controls](mac-private-key-controls.md) now construct it through the lifecycle coordinator; normal launcher setup remains off and key creation requires explicit review. The separate [durable key coordinator](private-key-lifecycle.md) now provides internal reviewed selection/replacement, restore locks and cleanup tracking in Mac task schema17. Registration, complete key rotation across peers, browser persistence, user-held endpoint recovery and live pairing remain open. Browser database version1, installed PR40 and prepared PR104 are unchanged; the new helper is included only in newly built development packages. Acer news processing and Mac model settings are unchanged and independent.

## Explicit creation and current authority

`PrivateEndpointKeys` receives a trusted local owner, owner-isolated slot factory and current lifecycle callback. The callback supplies a verified remote account/device/credential/lease, key ID, key epoch and whether this **fresh slot** may be created. These are not read from invitation, request, model output or stored secret bytes. The host must durably select fresh IDs/epochs, enforce replacement and capacity policy, and invalidate this provider immediately on pairing, permission or key changes. This module does not mint registration or permission.

Creation requires the exact current key ID/epoch and explicit confirmation. An atomic add-only attempt marker is written and read back **before** key generation. Missing keys after an interrupted attempt never trigger generation under that slot again. A lost acknowledgement after a successful key write can reopen the original key. A failed attempt without retained key bytes requires a fresh trusted lifecycle transition; deleting the marker to retry is prohibited. Concurrent creators cannot overwrite each other's secret.

The generated ECDH P-256 key is serialized once into a separate Keychain item, read back and verified, then reimported as a nonextractable runtime private handle. Public keys remain extractable for HPKE. A fresh ECDH agreement checks that the saved public and private keys correspond. Reads recheck current binding, immutable record and deletion marker; account, credential, lease and key changes deny reuse. Full binding equality is deliberately conservative: scoped lease renewal and historical-key recovery remain unfinished. Cached handles remain stable while authority and saved bytes are unchanged, with only a record digest retained alongside them. Returned pair containers cannot mutate that cache.

`invitation` requires an explicit intended recipient and returns only the existing strict public invitation plus full fingerprint, expiring within five minutes/current lease. The other endpoint must independently compare that fingerprint. Key possession/invitation generation does not grant task, source, result or action permission.

## Native storage and deletion

The `PrivateKeyInstall` helper owns reads, atomic add-only writes and key-only deletion in three fixed service names: `org.bittrees.ai.endpoint-keys`, `org.bittrees.ai.endpoint-key-attempts` and `org.bittrees.ai.endpoint-key-deletions`. Account names are domain-separated hashes of profile/local owner/key ID. New items retain the creator helper's ordinary Keychain access list; no all-application access is granted. The helper checks the caller's executable path through Security.framework and accepts only its sibling bundled Node runtime. This is an application component boundary, not protection against compromised code running through that runtime. Existing items and access lists are never rewritten.

Secret input/output is bounded to 4096 bytes and travels only through the adapter's private pipes, never arguments, environment or logs. Reads and writes use the same executable's Keychain identity, avoiding a cross-executable access prompt. Interaction is disabled: locked/untrusted access fails rather than waiting for a prompt. The adapter bounds output and kills an unresponsive helper after 15 seconds. There is no update operation; deletion is available only for key bytes, never safety markers. The legacy user-default Keychain APIs carry macOS deprecation warnings; signed-update trust and explicit unlock/access UI remain release gates. See Apple's [SecItemAdd contract](https://developer.apple.com/documentation/security/secitemadd(_:_:)) and [trusted-application access model](https://developer.apple.com/documentation/security/secaccesscreate(_:_:_:)).


Confirmed local deletion writes and verifies a permanent deletion marker before removing the key. Cleanup failure leaves the slot unusable and permits another cleanup attempt. A creator racing deletion removes any key written after the marker; it cannot return an active result. Attempt markers retain only a domain-separated identity hash; deletion markers retain a fixed flag. Neither contains key bytes. These markers intentionally remain after key removal to prevent accidental slot recreation. Deletion is available after lease expiry and does not claim remote revocation. The trusted host must revoke peer/operation permissions first and explain that deleting an unrecovered key can make history unreadable. Previously returned handles or independently exported copies cannot be recalled.

Raw bytes are wiped where practical; JSON strings, runtime copies and OS memory cannot be guaranteed erased. These are ordinary macOS Keychain secrets, not Secure Enclave keys or a claim of hardware nonexportability. Initial generation must be exportable to persist it; only the returned runtime handle is nonextractable, following the [WebCrypto ECDH key import/export model](https://www.w3.org/TR/webcrypto/#ecdh-operations). The local storage key, remote authentication credential and endpoint key remain separate items.

## Verification and integration requirements

Unit tests cover explicit creation/current binding, restart/same key, nonextractable handles, stable cache identity, actual peer fingerprint enrollment and HPKE, concurrent creators, uncertain native acknowledgements, interrupted generation, mismatched public/private records, missing/deleted keys, late revocation/deletion, owner/profile separation and host invalidation even if identity returns. The macOS packaging job uses the **packaged** helper and bundled Node with random disposable Keychain slots, exercising actual create/reopen/duplicate preservation, HPKE and deletion. A separately compiled untrusted native probe can locate the synthetic item but must be denied both its secret bytes and direct use of the helper. Test cleanup removes key bytes; minimal safety markers remain until the disposable runner is destroyed. No personal Keychain operation or local browser automation is used.

Before production activation, wire verified registration and the durable coordinator to real lifecycle controls, immediate host invalidation, final operation consent checks and the all-data cleanup hook; implement separately reviewed user-held endpoint recovery/export, browser keys and peer rotation; accept actual native access prompts and signed update trust; and obtain independent review. The existing storage recovery kit does not back up these separate endpoint-key items. Whole-Keychain deletion, hostile rollback or compromised local code can remove safety markers and remain outside this local mechanism; fresh external registration/reconciliation is required after such loss. No key import/restore or automatic regeneration fallback is provided.
