# Mac private endpoint key storage

Status: internal retained-key provider and packaged native helper. The companion launcher and HTTP routes do not construct it yet. This removes the need for ephemeral test keys at the Mac storage boundary; it does not complete registration, key rotation, browser persistence, user-held endpoint recovery or live pairing. Mac task schema16 and browser database version1 remain unchanged. Installed PR40 and prepared PR104 are unchanged; the new helper is included only in newly built development packages. Acer news processing and Mac model settings are unchanged and independent.

## Explicit creation and current authority

`PrivateEndpointKeys` receives a trusted local owner, owner-isolated slot factory and current lifecycle callback. The callback supplies a verified remote account/device/credential/lease, key ID, key epoch and whether this **fresh slot** may be created. These are not read from invitation, request, model output or stored secret bytes. The host must durably select fresh IDs/epochs, enforce replacement and capacity policy, and invalidate this provider immediately on pairing, permission or key changes. This module does not mint registration or permission.

Creation requires the exact current key ID/epoch and explicit confirmation. An atomic add-only attempt marker is written and read back **before** key generation. Missing keys after an interrupted attempt never trigger generation under that slot again. A lost acknowledgement after a successful key write can reopen the original key. A failed attempt without retained key bytes requires a fresh trusted lifecycle transition; deleting the marker to retry is prohibited. Concurrent creators cannot overwrite each other's secret.

The generated ECDH P-256 key is serialized once into a separate Keychain item, read back and verified, then reimported as a nonextractable runtime private handle. Public keys remain extractable for HPKE. A fresh ECDH agreement checks that the saved public and private keys correspond. Reads recheck current binding, immutable record and deletion marker; account, credential, lease and key changes deny reuse. Full binding equality is deliberately conservative: scoped lease renewal and historical-key recovery remain unfinished. Cached handles remain stable while authority and saved bytes are unchanged, with only a record digest retained alongside them. Returned pair containers cannot mutate that cache.

`invitation` requires an explicit intended recipient and returns only the existing strict public invitation plus full fingerprint, expiring within five minutes/current lease. The other endpoint must independently compare that fingerprint. Key possession/invitation generation does not grant task, source, result or action permission.

## Native storage and deletion

The new `PrivateKeyInstall` helper uses add-only `SecItemAdd` against three fixed service names: `org.bittrees.ai.endpoint-keys`, `org.bittrees.ai.endpoint-key-attempts` and `org.bittrees.ai.endpoint-key-deletions`. Account names are domain-separated hashes of profile/local owner/key ID. New items grant read access to exactly the creator helper and its sibling bundled Node executable, using Apple's [trusted-application access list](https://developer.apple.com/documentation/security/secaccesscreate(_:_:_:)). No all-application grant or caller-selected reader path is accepted. Existing items and their access lists are never modified. Access-list behavior across signed updates and actual user prompts remains a release gate. The helper accepts at most 4096 bytes through a private stdin pipe; it has no update/delete operation and receives no secret in arguments, environment or logs. Duplicate creation reports an existing item rather than changing it. The helper targets the same user-default Keychain as the existing native addon; its legacy default-Keychain/access-list APIs carry macOS deprecation warnings and needs reassessment alongside future native storage changes. Reads normalize the native addon's number-array/null response into owned bytes. The adapter's key deletion uses the matching native Keychain entry. See Apple's [SecItemAdd contract](https://developer.apple.com/documentation/security/secitemadd(_:_:)).

Confirmed local deletion writes and verifies a permanent deletion marker before removing the key. Cleanup failure leaves the slot unusable and permits another cleanup attempt. A creator racing deletion removes any key written after the marker; it cannot return an active result. Attempt markers retain only a domain-separated identity hash; deletion markers retain a fixed flag. Neither contains key bytes. These markers intentionally remain after key removal to prevent accidental slot recreation. Deletion is available after lease expiry and does not claim remote revocation. The trusted host must revoke peer/operation permissions first and explain that deleting an unrecovered key can make history unreadable. Previously returned handles or independently exported copies cannot be recalled.

Raw bytes are wiped where practical; JSON strings, runtime copies and OS memory cannot be guaranteed erased. These are ordinary macOS Keychain secrets, not Secure Enclave keys or a claim of hardware nonexportability. Initial generation must be exportable to persist it; only the returned runtime handle is nonextractable, following the [WebCrypto ECDH key import/export model](https://www.w3.org/TR/webcrypto/#ecdh-operations). The local storage key, remote authentication credential and endpoint key remain separate items.

## Verification and integration requirements

Unit tests cover explicit creation/current binding, restart/same key, nonextractable handles, stable cache identity, actual peer fingerprint enrollment and HPKE, concurrent creators, uncertain native acknowledgements, interrupted generation, mismatched public/private records, missing/deleted keys, late revocation/deletion, owner/profile separation and host invalidation even if identity returns. The macOS packaging job uses the **packaged** helper, bundled Node and installed native addon with random disposable Keychain slots, exercising actual create/reopen/duplicate preservation, HPKE and deletion. A separately compiled untrusted native probe can locate the synthetic item but must be denied its secret bytes with interaction disabled. It removes only those synthetic slots. No personal Keychain operation or local browser automation is used.

Before production activation, implement durable registration/key selection and monotonic rotation/revocation with bounded retained slots; wire immediate host invalidation and final operation consent checks; implement separately reviewed user-held endpoint recovery/export and browser keys; integrate deletion with all-data controls; accept actual native access prompts and signed update trust; and obtain independent review. The existing storage recovery kit does not back up these separate endpoint-key items. Whole-Keychain deletion, hostile rollback or compromised local code can remove safety markers and remain outside this local mechanism; fresh external registration/reconciliation is required after such loss. No key import/restore or automatic regeneration fallback is provided.
