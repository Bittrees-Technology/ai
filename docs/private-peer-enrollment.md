# Local private-peer enrollment foundation

Status: internal enrollment/review and persistence backend. No invitation exchange, browser/native fingerprint UI, reciprocal enrollment, endpoint private-key storage, relay route or task dispatcher calls it yet. It must not be described as a completed device-pairing or private-remote-access feature. It supplies trusted public-key lookup for the [private-envelope codec](private-remote-envelopes.md), with explicit next-layer authority checks.

## Review and approval

`inspectPrivateInvitation` accepts a strict versioned invitation: remote owner UUID, intended local recipient-device UUID, peer-device UUID, positive key epoch, canonical raw P-256 public key, random invitation UUID and a lifetime of at most five minutes. It validates the actual curve point and hashes a fixed, domain-separated encoding of every field. The full SHA-256 fingerprint must be independently compared with the other trusted endpoint. A fingerprint merely echoed by the relay or copied from this same received invitation is not an out-of-band check or proof of ownership.

`PrivatePeerEnrollment` obtains local owner scope at construction and the current verified remote account/device/credential epoch/lease through a trusted synchronous provider. The provider must observe pairing loss/rotation immediately; it must never read identity from an envelope, invitation or arbitrary request body. Preparing a review checks the account and recipient, imports the key, snapshots the current registry revision, then rechecks state after asynchronous work. At most four unexpired reviews are held in memory. Restart loses reviews; none can silently turn into approval.

Approval requires the one-use review ID, reviewed registry revision, exact compared fingerprint and explicit confirmation. The original internally captured invitation is used, not a caller-supplied replacement. A SQLite immediate transaction rechecks current pairing, expiry and registry revision before changing the pin. Concurrent approvals and stale reviews fail rather than overwriting each other. An uncertain caller outcome should be resolved by reading the current registry; blind replay is not an approval recovery mechanism.

This backend enforces the confirmation contract; it cannot establish that a human actually compared the fingerprints. The eventual UI must make account/device identity and key replacement clear, must not auto-fill an assertion of out-of-band comparison, and must invalidate reviews when hidden or changed. Mutual possession/reciprocal enrollment, authenticated invitation exchange and actual user acceptance are still required before activation.

## Rotation, revocation and use

The registry retains up to 20 peer slots and 512 retired key records. Replacement needs a different public key, a strictly higher peer key epoch and a fresh fingerprint review. Previously used keys cannot be reused for the same or another peer. Retired key hashes and per-peer epoch history survive a normal binding reset; capacity exhaustion fails rather than automatically pruning revocation history. Whole-data deletion is described below.

Local revocation remains available even when the remote lease is absent or expired. It cannot unlock restored trust. Changing the remote binding requires a confirmed reset, which removes active peers while retaining retirement history. A different remote account, device, credential epoch or lease never silently inherits the previous pins.

Resolving a pin returns a WebCrypto public key plus a revision-bound proof. Public keys are extractable because HPKE serializes them; no private key is exported or stored here. Revocation, replacement, another registry change, account change, expiry, restore or deletion invalidates that proof, including changes during asynchronous public-key import. **The caller must validate it again after decryption and within final local acceptance checks.** Receiving bytes or possessing a pin is not permission to execute a task, bypass source authority, approve a proposal or consume a replay. Durable inbox/outbox/replay state remains a separate prerequisite.

## Storage, export, deletion and recovery

Task schema **13** adds one owner-scoped registry row. Pairing metadata, public pins and retirement history are encrypted with the existing Vault using owner-specific associated data. Cross-owner ciphertext copies fail authentication. Existing authenticated local JSON export includes `privatePeerTrust`; it grants no trust and includes no private key. The internal nonreversible device-anchor hash is not exported.

Coordinated/task backup restoration locks each registry and advances its revision before publishing the restored database. A credential-epoch change alone cannot unlock it. The local device must be paired with a **different device UUID**, followed by an explicit reset and fresh key reviews. Old peer keys remain retired; no restored peer is automatically trusted. This reduces accidental authority rollback through the supported restore path. It does not prove resistance to malicious whole-filesystem/OS rollback or a compromised endpoint; final R2 restore/replay reconciliation and independent review remain open.

Confirmed whole-data deletion clears the encrypted registry payload, including public keys and retirement history. A bounded row containing local owner identifiers, revision, lock flag and keyed device-anchor hash remains solely to prevent the old local identity from silently resetting trust. It contains no raw remote account/device ID, public key or invitation. A fresh local device pairing is required before resetting this marker. Deletion cannot retract already exported copies or backups. Endpoint private-key/recovery storage is not implemented by this module.

An older engine must not open a schema-13 database. Rollback requires the original compatible backup restored to a separate path. The [synthetic compatibility receipt](evidence/private-peer-schema-compatibility-2026-09-22.json) uses the actual previously prepared PR104 runtime: it seeds schema12, preserves its task through the current schema13 upgrade, proves the old engine refuses schema13, and restores the original schema12 backup with that old engine. The old bundle's source receipt and deep/strict signature were verified. Reproduce after building current source using `BITTREES_OLD_APP_RESOURCES` with the reviewed PR104 Resources directory and `node scripts/check-private-peer-upgrade.mjs`; optionally set `BITTREES_COMPAT_RECEIPT` to a new receipt file. Only disposable synthetic stores are used.
