# Browser storage for outgoing private envelopes

Status: internal browser storage backend. `BrowserPrivateOutbox` persists original encrypted wire messages in IndexedDB for retry after reload. The production remote dashboard imports it through the retained consent module, but has no task dispatch, network sender, task form, automatic background work or recovery-import path. The outbox itself is not an endpoint-secret store. Current Mac task schema23 is unchanged. Browser task records now share endpoint database version5 with retained keys and peer pins, using the [restartable legacy-outbox migration](browser-private-storage.md). The old separate version1 database is fenced at version2. Optional receipt/result fields retain their null defaults. A production update/rollback policy remains required before activation.

## Stored data and authority

This backend stores HPKE ciphertext, authenticated routing headers, reviewed peer/permission revisions, reservation/acceptance state and handoff counts. Accepted entries retain encrypted receipt and/or result envelopes and domain-separated semantic hashes for idempotency. The result receipt time is metadata. Plaintext receipt/task IDs and output text are not persisted. The hash is not a secret or an authorization token. No plaintext prompt, result or task body is written. Outbox records contain no endpoint private keys or cloud credentials; the common database separately retains the existing nonextractable endpoint-key handles. Receipt verification receives in-memory CryptoKey handles through the trusted callback; it does not export or serialize them. Routing/account/device metadata is visible in the local browser store, as it is in wire headers. It is not a complete conversation-history or key backup: outgoing task text remains opaque to the browser outbox, and the companion owns its full local task history. Accepted result ciphertext can be explicitly reopened under current authority.

The internal [retained consent provider](browser-task-consent.md) supplies actual retained key/peer/completed-check/permission validation inside every outbox transaction. Callback-only `open` remains for legacy compatibility and protocol fixtures. The trusted host must supply current **verified** account/device binding and keep that scope alive throughout each task operation; host task dispatch is still unmounted. Stored context, invitation data, request fields and model text are never authority sources. Every operation checks the current account/lease, and reserve/commit/handoff additionally check the exact current peer/key/permission context. These checks run again in IndexedDB callbacks and before returning a transaction result. They observe the client's current verified state; they do not promise instant remote revocation while offline.

Opening the database does not enroll a device or initialize counters. Explicit confirmed initialization additionally requires a trusted fresh-registration callback matching the active binding. That callback must be available only for a just-issued fresh endpoint registration, never reconstructed from stored rows or an old session after storage loss. A missing database fails ordinary operations with `SETUP_REQUIRED`. Verified registration/key setup exists separately; task dispatch/UI wiring is not implemented here.

## Reservation and persistence

A short read/write transaction reserves a new operation/message UUID and a monotonically increasing sequence for the directed endpoint/key-epoch channel. The counter and `reserved` entry commit together. No cryptography or network promise runs inside an IndexedDB transaction; callbacks queue dependent database requests while the transaction is active. Success is returned only after `complete`, using the strict durability hint supported by the tested engines.

The caller encrypts its reviewed task using the existing codec outside that transaction, then commits the envelope against the exact reservation header and revision. Envelope parsing requires strict fields and canonical bounded ciphertext/encapsulation encodings. This is structural validation, **not authentication or permission to execute**; the actual destination must use HPKE and its guarded receiver. A committed pending envelope is immutable. Exact commit retry returns the existing entry; altered ciphertext/header or a stopped reservation cannot replace it. Concurrent tabs serialize through database transactions, so sequence allocation and competing commits cannot publish conflicting entries under one reservation.

A `reserved` entry has no prompt or ciphertext. If the page disappears before encryption commits, it cannot be sent. Reopening does not silently regenerate content, advance deadlines or start a new operation. Recovery of an unfinished reservation needs an explicit fresh task review in the future UI. Pending entries retain the original ciphertext; `delivery` checks current authority and expiry, records a handoff attempt transactionally and returns an exact copy. Exported rows and earlier handoff results are not reusable delivery authorizations. Bytes already handed to a transport cannot be recalled by a later stop or permission change.

Local `stop` is confirmed and revision-checked. The callback-only API allows it without per-peer sending permission while the account binding remains valid; the retained guarded instance requires current consent for all operations. A separate trusted owner-local offline maintenance path must be wired before task controls are exposed. It stops local handoffs and does not claim destination cancellation. No API can mark a plaintext relay response as accepted. `acceptReceipt` authenticates the encrypted destination receipt using current trusted endpoint keys and reviewed peer context, as described below. Handoff count is not proof of transmission, acceptance, reading or completion.

## Authenticated destination acceptance

`acceptReceipt` locates the original operation, requires a committed task envelope, and checks reversed account/device/key-epoch routing. A separate trusted key provider must supply the current recipient key pair and reviewed destination public key with the exact same verified context as the outgoing entry. The module never imports a key from a receipt or persisted row. Trusted integration must bind that public key to the reviewed fingerprint; this callback is not a replacement for real enrollment.

HPKE authentication, strict UTF-8/task.accepted parsing, complete original-header equality and plausible acceptance-time checks happen outside database transactions. Plaintext buffers are cleared after parsing, subject to JavaScript memory-erasure limits. A final transaction rechecks the live account, peer/permission context, exact key object identities, receipt expiry and deletion lock before saving the encrypted receipt and semantic hash. Quota failure rolls back both status and metadata revision. Exact receipt content is idempotent even when the destination reseals it; changed receipt content for an accepted operation conflicts. An entry with an authenticated acceptance or embedded result receipt cannot be sent or changed to stopped. The original committed ciphertext remains available for export.

A valid late receipt can reconcile an already-stopped task, since local stop never proved destination cancellation. Acceptance means **queued at the destination**, not execution, completion or a verified answer. Original task expiry does not erase historical acceptance, but the current account/permission/key context and new receipt envelope must still be valid. Changed/expired account bindings require future scoped reconciliation, not silent authority renewal. Reopening storage preserves accepted status/ciphertext without saving keys; processing a new receipt still needs current verified keys. Retained consent now supplies persistent endpoint keys; transport and production task UI are not wired here. The internal [response review screen](private-results-review.md) is exercised only in the synthetic browser fixture. The separate [companion response backend](private-task-responses.md) produces receipts/results; only the disposable test harness currently connects it to this browser backend.

## Durable result acceptance and explicit reading

`acceptResult` authenticates the strict `task.result` payload with the current reviewed destination key. It requires the original committed request, reversed routing/key epochs, a matching embedded acceptance receipt, the matching task ID, a terminal status and plausible update time. Result reception and reading additionally require `resultsEnabled: true` from the trusted key provider. Receipt-only permission does not enable result access. Raw relay status, source/model/authority fields, wrong keys/tasks, impossible times and tampered envelopes are rejected.

A result may arrive before the separate acceptance message. Its authenticated embedded receipt establishes acceptance and stops outgoing retries. Later receipt delivery must match that exact semantic receipt; it can add its own encrypted envelope without changing the result. Receipt-first, result-first, concurrent and resealed duplicates reconcile transactionally. The first accepted terminal result is immutable. Different output, revision, status or receipt conflicts rather than silently replacing history. Results arriving after a local retry stop remain evidence of destination activity; stop never proved cancellation.

Only result ciphertext, semantic hashes and received time are saved. `readResult` requires explicit confirmation and the reviewed entry revision, current account/peer permission and keys. It reauthenticates/decrypts the saved envelope, rechecks the semantic hashes, then uses a final read transaction to recheck authority, key object identity, unchanged revision/content and deletion state before returning plaintext. No plaintext is cached by this module. Calling UI must treat returned model text as untrusted plain text and clear previews on account/permission/focus changes; bytes already returned cannot be recalled.

Transport expiry is distinct from historical viewing. New incoming envelopes must be unexpired. A result already authenticated and stored while valid may be reopened using its recorded receipt time **only for cryptographic historical verification**. Current account/permission/key checks still use the current clock, and reading never dispatches, renews authority or changes status. Corrupted ciphertext/hash, future received times and invalid stored time bounds fail. Whole-origin/storage rollback or compromised same-origin code is outside this storage guarantee. Changed/expired identity bindings still need the separate future scoped renewal/recovery flow; retained ciphertext is not authorization to reveal it.

Optional fields preserve reads of earlier version1 rows, while older code fails closed on the new fields. The records now live in shared browser database version5; current Mac task schema23 is unchanged. Export/deletion include result ciphertext and hashes. Key loss still prevents decryption. Tests re-inject the same **synthetic** keys after a full reload to verify ciphertext recovery; those legacy protocol tests do not implement private-key persistence or real recovery. Retained-consent tests additionally use the actual retained browser and Mac providers across reload.

## Export, deletion and storage loss

Owner-scoped export returns encrypted outgoing rows and their metadata under the current account binding. No automatic expiry pruning occurs. Limits are 256 retained entries per account, 32 account markers per origin, 1024 shared channels per account and eight in-flight operations per instance; capacity failure preserves earlier data. Opens and transactions have bounded waits. Quota/transaction/connection/version errors fail with fixed codes, without a volatile-memory or plaintext fallback.

Confirmed deletion uses the reviewed account metadata revision. One transaction removes its entries, preserves minimal shared sequence counters, and locks a minimal marker containing domain-separated hashes of the account and current device plus a revision. Stale tabs cannot recreate an old reservation after that deletion. Reinitialization requires a different newly registered device identity. The hashes are fences, not secrets or unlinkability for someone who already knows the IDs. Old ciphertext already exported or handed to transport is an independent copy.

A database version change closes the old connection and denies later use; a newer unknown version is not downgraded or reset. Missing/evicted/cleared storage is not automatically initialized. However, the browser can remove the entire database including its deletion marker. Protection after that event depends on the **fresh external registration and endpoint-key lifecycle**, not this database alone. Whole-filesystem rollback, compromised same-origin scripts/clients, quota pressure, OS power loss and browser backup semantics are not solved by this module. There is no browser restore/import endpoint that can revive old queued authority. User-held key recovery, persistent-storage UX, browser backup and explicit restoration review remain open.

## Verification and sources

The existing CI job builds the fixture and runs it in Chromium, Firefox and WebKit on disposable GitHub runners. Added scenarios use real IndexedDB for page reload/exact retry into the real companion receiver, concurrent tabs/sequence allocation/competing ciphertext, reviewed deletion/stale-tab fencing/new-device setup, account isolation and permission-loss stop, reservation/deletion transaction rollback under injected quota exceptions and late revocation, expiry/version change, retained capacity and missing-storage denial after explicit whole-database removal. The quota exception is injected into an actual database operation; it is not a physical disk-full or OS-eviction test. Result tests add either delivery order, reload with synthetic key reinjection, current permission/key/revision checks, immutable conflicting-result denial, result quota rollback, invalid/tampered input, historical viewing after delivery expiry and deletion during in-flight decryption. Additional receipt scenarios cover real companion admission, encrypted acceptance persistence/reload, resealed and concurrent duplicates, stopped-task reconciliation, forged/mismatched/conflicting/impossible receipts, late permission/key changes and rollback under injected quota failure. Keys and verified authority are synthetic fixtures, not completed human pairing or personal browser acceptance.

Implementation follows the documented [IndexedDB transaction activity and completion rules](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction), [blocked-open behavior](https://developer.mozilla.org/en-US/docs/Web/API/IDBOpenDBRequest/blocked_event) and [browser quota/eviction limits](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria). Strict durability is a requested browser hint, not a hardware durability guarantee.

Retained endpoint keys, user-held recovery, verified registration and public peer review now have separate implementations. Reciprocal possession checks and retained consent/outbox authority now have separate implementations. Remaining before activation: trusted host task dispatch, task/response/result UI, durable preparation/reconciliation, transport/relay and its pending retention choice, recovery/offline UX, independent protocol review and personal Safari/WKWebView acceptance. The installed Mac app, prepared archive, cloud settings and Acer's existing news model/runtime remain unchanged.
