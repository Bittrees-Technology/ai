# Browser storage for outgoing private envelopes

Status: internal browser storage backend. `BrowserPrivateOutbox` persists original encrypted wire messages in IndexedDB for retry after reload. It is not imported by the production remote dashboard and has no network sender, task form, endpoint-secret store, automatic background work or recovery-import path. Existing Mac task schema15 is unchanged; this uses a separate browser database, version1. Optional receipt-envelope/hash fields default to null for earlier version1 rows; no destructive upgrade is performed. Older client code rejects the new fields/state, so it cannot resume entries written in the new format. A production client update/rollback policy remains required before activation.

## Stored data and authority

This backend stores HPKE ciphertext, authenticated routing headers, reviewed peer/permission revisions, reservation/acceptance state and handoff counts. Accepted entries also retain the encrypted receipt envelope and a domain-separated hash of the validated receipt for idempotency; plaintext receipt/task IDs are not persisted. The hash is not a secret or an authorization token. It never persists prompts, results, plaintext tasks, endpoint private keys or cloud credentials. Receipt verification receives in-memory CryptoKey handles through the trusted callback; it does not export or serialize them. Routing/account/device metadata is visible in the local browser store, as it is in wire headers. It is not a complete encrypted browser history or a backup of the user's task content; accepted local history remains owned by the companion.

The integration must supply current **verified** account/device binding and per-peer sending authority through trusted callbacks. Stored context, invitation data, request fields and model text are never authority sources. Every operation checks the current account/lease, and reserve/commit/handoff additionally check the exact current peer/key/permission context. These checks run again in IndexedDB callbacks and before returning a transaction result. They observe the client's current verified state; they do not promise instant remote revocation while offline.

Opening the database does not enroll a device or initialize counters. Explicit confirmed initialization additionally requires a trusted fresh-registration callback matching the active binding. That callback must be available only for a just-issued fresh endpoint registration, never reconstructed from stored rows or an old session after storage loss. A missing database fails ordinary operations with `SETUP_REQUIRED`. Final real registration/key/UI wiring is not implemented here.

## Reservation and persistence

A short read/write transaction reserves a new operation/message UUID and a monotonically increasing sequence for the directed endpoint/key-epoch channel. The counter and `reserved` entry commit together. No cryptography or network promise runs inside an IndexedDB transaction; callbacks queue dependent database requests while the transaction is active. Success is returned only after `complete`, using the strict durability hint supported by the tested engines.

The caller encrypts its reviewed task using the existing codec outside that transaction, then commits the envelope against the exact reservation header and revision. Envelope parsing requires strict fields and canonical bounded ciphertext/encapsulation encodings. This is structural validation, **not authentication or permission to execute**; the actual destination must use HPKE and its guarded receiver. A committed pending envelope is immutable. Exact commit retry returns the existing entry; altered ciphertext/header or a stopped reservation cannot replace it. Concurrent tabs serialize through database transactions, so sequence allocation and competing commits cannot publish conflicting entries under one reservation.

A `reserved` entry has no prompt or ciphertext. If the page disappears before encryption commits, it cannot be sent. Reopening does not silently regenerate content, advance deadlines or start a new operation. Recovery of an unfinished reservation needs an explicit fresh task review in the future UI. Pending entries retain the original ciphertext; `delivery` checks current authority and expiry, records a handoff attempt transactionally and returns an exact copy. Exported rows and earlier handoff results are not reusable delivery authorizations. Bytes already handed to a transport cannot be recalled by a later stop or permission change.

Local `stop` is confirmed and revision-checked; it remains available when per-peer sending permission is absent but the account binding is still valid. It stops local handoffs and does not claim destination cancellation. No API can mark a plaintext relay response as accepted. `acceptReceipt` authenticates the encrypted destination receipt using current trusted endpoint keys and reviewed peer context, as described below. Handoff count is not proof of transmission, acceptance, reading or completion.

## Authenticated destination acceptance

`acceptReceipt` locates the original operation, requires a committed task envelope, and checks reversed account/device/key-epoch routing. A separate trusted key provider must supply the current recipient key pair and reviewed destination public key with the exact same verified context as the outgoing entry. The module never imports a key from a receipt or persisted row. Trusted integration must bind that public key to the reviewed fingerprint; this callback is not a replacement for real enrollment.

HPKE authentication, strict UTF-8/task.accepted parsing, complete original-header equality and plausible acceptance-time checks happen outside database transactions. Plaintext buffers are cleared after parsing, subject to JavaScript memory-erasure limits. A final transaction rechecks the live account, peer/permission context, exact key object identities, receipt expiry and deletion lock before saving the encrypted receipt and semantic hash. Quota failure rolls back both status and metadata revision. Exact receipt content is idempotent even when the destination reseals it; changed receipt content for an accepted operation conflicts. An accepted entry cannot be sent or changed to stopped. The original committed ciphertext remains available for export.

A valid late receipt can reconcile an already-stopped task, since local stop never proved destination cancellation. Acceptance means **queued at the destination**, not execution, completion or a verified answer. Original task expiry does not erase historical acceptance, but the current account/permission/key context and new receipt envelope must still be valid. Changed/expired account bindings require future scoped reconciliation, not silent authority renewal. Reopening storage preserves accepted status/ciphertext without saving keys; processing a new receipt still needs current verified keys. No persistent key provider, destination receipt producer, result channel, transport or production UI is wired here.

## Export, deletion and storage loss

Owner-scoped export returns encrypted outgoing rows and their metadata under the current account binding. No automatic expiry pruning occurs. Limits are 256 retained entries per account, 32 account markers per origin and eight in-flight operations per instance; capacity failure preserves earlier data. Opens and transactions have bounded waits. Quota/transaction/connection/version errors fail with fixed codes, without a volatile-memory or plaintext fallback.

Confirmed deletion uses the reviewed account metadata revision. One transaction removes its entries and counters and locks a minimal marker containing domain-separated hashes of the account and current device plus a revision. Stale tabs cannot recreate an old reservation after that deletion. Reinitialization requires a different newly registered device identity. The hashes are fences, not secrets or unlinkability for someone who already knows the IDs. Old ciphertext already exported or handed to transport is an independent copy.

A database version change closes the old connection and denies later use; a newer unknown version is not downgraded or reset. Missing/evicted/cleared storage is not automatically initialized. However, the browser can remove the entire database including its deletion marker. Protection after that event depends on the **fresh external registration and endpoint-key lifecycle**, not this database alone. Whole-filesystem rollback, compromised same-origin scripts/clients, quota pressure, OS power loss and browser backup semantics are not solved by this module. There is no browser restore/import endpoint that can revive old queued authority. User-held key recovery, persistent-storage UX, browser backup and explicit restoration review remain open.

## Verification and sources

The existing CI job builds the fixture and runs it in Chromium, Firefox and WebKit on disposable GitHub runners. Added scenarios use real IndexedDB for page reload/exact retry into the real companion receiver, concurrent tabs/sequence allocation/competing ciphertext, reviewed deletion/stale-tab fencing/new-device setup, account isolation and permission-loss stop, reservation/deletion transaction rollback under injected quota exceptions and late revocation, expiry/version change, retained capacity and missing-storage denial after explicit whole-database removal. The quota exception is injected into an actual database operation; it is not a physical disk-full or OS-eviction test. Additional receipt scenarios cover real companion admission, encrypted acceptance persistence/reload, resealed and concurrent duplicates, stopped-task reconciliation, forged/mismatched/conflicting/impossible receipts, late permission/key changes and rollback under injected quota failure. Keys and verified authority are synthetic fixtures, not completed human pairing or personal browser acceptance.

Implementation follows the documented [IndexedDB transaction activity and completion rules](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction), [blocked-open behavior](https://developer.mozilla.org/en-US/docs/Web/API/IDBOpenDBRequest/blocked_event) and [browser quota/eviction limits](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria). Strict durability is a requested browser hint, not a hardware durability guarantee.

Remaining before activation: persistent endpoint keys and user-held recovery, real fresh registration/peer review/consent callbacks, receipt producer/result handling, transport/relay and its pending retention choice, task/recovery/offline UX, independent protocol review and personal Safari/WKWebView acceptance. The installed Mac app, prepared archive, cloud settings and Acer's existing news model/runtime remain unchanged.
