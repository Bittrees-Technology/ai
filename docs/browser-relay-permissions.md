# Browser relay permission review

Browser permission enablement now requires the exact reviewed `deviceId` and `credentialEpoch`, in addition to the operation ID, expected prior permission, expiry and explicit confirmation. The server compares those fields against the current authenticated browser registration inside its existing locked transaction, before replacing or creating any permission. A newly registered browser cannot inherit a pending approval for its predecessor even when the owner session is unchanged.

Mac approval already names its exact device and epoch. Both browser and Mac input shapes use the same endpoint approval schema. Existing synthetic integration and browser fixtures now send the registration they actually observed. Missing identity fields are invalid input; mismatched current identity is denied without creating a permission. Actual PostgreSQL/HTTPS tests cover wrong identity/epoch, missing fields and same-owner registration replacement.

## Bounded owner metadata client

`BrowserRelayPermissionsClient` uses the existing fixed-origin bounded transport, HttpOnly browser cookies and current owner/session scope. It verifies exact owner, endpoint, credential epoch, operation ID, expiry and revision on approval; bounded ordered permission pages; owner history and revocation; and rejects unexpected fields, including returned credentials. Scope changes and explicit invalidation discard late responses. Lost mutation replies require a separate explicit lookup by the original operation ID; no automatic retry is added.

The owner-only `/browser/relay/permissions/endpoint` route validates the exact current endpoint and credential epoch under the same authority transaction and returns its current nonrevoked permission or null. An existing permission may retain an earlier credential epoch after rotation: this is displayed replacement metadata, not usable authority. This avoids inferring absence from a partial history page. The endpoint route remains absent without explicit private relay policy.

Seven new engine cases verify the client. Two additional actual-browser scenarios (six cases across Chromium/Firefox/WebKit) cover rotation, paged history, owner revocation and cancellation using real HttpOnly cookies. These are authored and built, with execution reserved for disposable GitHub CI. Actual HTTPS/PostgreSQL integration covers endpoint absence, exact browser/Mac identity, cross-owner/epoch/CSRF denial, credential rotation, revoked/expired endpoints, owner client approval/replacement, explicit operation lookup, bounded history and revocation.

## Visible owner controls

When the remote host has a complete validated private policy, `/settings.json` advertises `privateRelay: true`. Only then does the signed-in page mount Private message connections. The default settings response and hidden section are unchanged when policy is absent. This is a feature-availability signal, not authority; all routes still authenticate and check the owner and endpoint in their transaction.

The page reviews this browser's current registration or a selected current paired Mac. A review displays exact account/device/credential version, the previous permission, replacement effect and proposed expiry (up to one hour, capped by endpoint expiry). An acknowledgement enables a single confirmation; the review expires within two minutes. Mac approval displays an ID and deadline for separate native acceptance. Owner history and fresh-revision revocation work independently of endpoint secrets.

An uncertain response retains the original operation ID (or permission ID for revocation) for explicit read-only checking. Confirmation is consumed before the network call and never retried automatically. If inspection cannot resolve an uncommitted/lost request, an acknowledged local-reference removal permits a new review of the current permission; it does not claim the original action failed or undo it. Operation references are in-memory; owner permission history remains available after leaving the page.

Account/scope changes discard visible metadata and invalidate in-flight requests. Blur, visibility changes, Escape and page exit cancel reviews and suppress late results, while preserving an uncertain operation within the same account. Review confirmation also checks wall and monotonic clocks. Idle host updates preserve the review DOM and keyboard focus; a changed device list can require acknowledgement again. Permissions are independent of encryption keys, peer trust, task consent and automatic delivery.

Seven UI-controller tests cover one-use acknowledgement, exact immutable review data, lost replies, fresh revocation revisions, expired/rolled-back/account-changed reviews, late replies and deliberate uncertain-reference removal. Three shipped-page browser scenarios (nine cases across Chromium/Firefox/WebKit) exercise real TLS, HttpOnly cookies, owner registration, pending Mac acceptance, revocation, response-loss recovery, Escape and narrow layout. They retain 18 screenshots. Together with the metadata browser cases, the expected full suite is 1,032 cases. Browser execution and visual inspection remain pending disposable GitHub CI; local typecheck, all637 engine tests, production/fixture builds and full actual HTTPS/PostgreSQL pass.

No live policy, migration, service, personal Keychain or installed app is changed. The Mac companion model remains separate from the unchanged Acer news model/runtime. Durable message transport, live retention/hosting and independent acceptance remain open.
