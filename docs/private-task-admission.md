# Private task admission on the local companion

This internal R2 receiver connects the private-envelope codec and reviewed peer registry to the existing local task queue. It is not wired to startup, a network route, relay, native UI or installed app. Hosted private task submission remains unavailable. Endpoint key persistence, real per-peer consent, fingerprint comparison UI, reciprocal enrollment, ciphertext delivery and independent review remain required before activation.

## Permission and accepted content

`PrivateTaskReceiver` receives local owner scope, the current verified remote account/device binding, and a synchronous trusted provider of **explicit per-peer task consent**. That provider supplies a current permission revision, locally selected model profile, active recipient key pair and key epoch. These are internal authority inputs, never fields taken from an envelope, model, invitation or relay. Public-key approval alone does not grant task submission. Future integration must persist/revoke this consent and clear it during restore; constructing a provider that always permits would bypass this boundary and is not an acceptable integration.

A candidate envelope must match the current account, recipient and key epoch and resolve the sender's reviewed, unrevoked public key. HPKE authentication and the strict inner schema must succeed. After all asynchronous work, an immediate SQLite transaction rechecks the same permission, pairing, key references, registry proof and envelope expiry before committing anything. Account/credential/key/consent changes, lost pairing, revocation and expiry deny admission. Unknown internal errors return a fixed error without raw content or crypto causes. No plaintext fallback exists.

The first payload is strictly `{ version: 1, type: "task.submit", kind: "query" | "summarize" | "draft", prompt }`. The prompt is bounded to 32,000 UTF-16 units and the enclosing codec to 65,536 plaintext bytes. UTF-8 decoding rejects invalid encoding. Additional fields are rejected. The receiver generates a new local conversation and task, using the locally authorized model profile. The sender cannot select an existing conversation, model, memory, source records/grants, dependency, priority, action, approval or tool. Local inference uses the existing worker; generated text grants no write/send authority.

Consent is checked for **admission**. A committed source-free task becomes local history/work; revoking future submission consent does not retract or automatically cancel an already accepted task. Existing local task controls can cancel it. Source-bound tasks and externally effective actions require their own source checks and exact approval paths and are not accepted by this payload. Consent UI must explain this distinction before enabling it.

## Atomic acceptance and retries

Task schema **14** adds `private_task_receipts`. The task, conversation sequence, ordinary task idempotency/event records and receipt commit in one SQLite transaction. A receipt insertion failure rolls back all of them. No model work or network action occurs in that transaction.

Receipt lookup uses keyed, domain-separated hashes of operation ID, message ID and directed endpoint/key-epoch sequence. Operation/message identity is scoped to the local owner and remote account, across sender/device/key rotation. Sequence identity is scoped to both endpoint IDs and their key epochs. The authenticated envelope has a separate keyed hash. Every accepted identity is retained; out-of-order sequence numbers are accepted only once. There is no unbounded sparse sequence bitmap or silent pruning.

An exact authenticated envelope retry returns the original immutable receipt and task ID, including after restart or after the task completes. A different ciphertext, header, operation/message association or reused sequence conflicts. Re-encrypting a retry creates new ciphertext and therefore conflicts: the future sender must persist and retry its original envelope. Concurrent duplicate transactions, including across SQLite connections, create one task. Concurrent conflicting ciphertext has one winner. These are local durable creation guarantees, not exactly-once model execution or external effects under process/OS failure.

Receipts mean **accepted into the local queue**, not running, completed, read or published. Current permission, peer trust and envelope expiry still apply to duplicate delivery; expired/revoked retries do not return a receipt through this receiver. Existing local export retains the original receipt for inspection. An authenticated remote reconciliation/result protocol remains to be implemented.

The receiver holds at most four cryptographic operations concurrently per instance. The database caps receipts at 1,024 per local owner and fails new admissions at capacity; it never evicts replay records. Duplicate receipts still resolve at capacity. A future transport must additionally apply global request/body/rate limits before parsing. There is no hosted quota or network protection claim from these local bounds.

## Local content, backup and deletion

Receipt payloads (header, receipt/task IDs, acceptance time and consent revision) are encrypted with owner- and operation-specific Vault associated data. SQL indexes contain keyed hashes and local owner IDs, not prompts or raw remote identifiers. Task prompts use the existing encrypted task store. Neither endpoint private keys nor original wire ciphertext is stored by this receiver. Local authenticated JSON export includes owner-scoped `privateTaskReceipts`; this is private content, never a remote-status projection.

Receipts/history remain until confirmed local data deletion. Deletion removes receipts with tasks and locks the peer registry using its existing device-anchor marker. Supported task/coordinated backup restoration preserves receipt evidence but locks peer trust. The old device cannot resume admission; fresh device pairing and key reviews are required. This prevents old envelopes from bypassing replay checks through the supported restore/delete path. It does not protect against hostile filesystem rollback, compromised clients, or unauthorized code supplying fake trusted providers. Original backups and exports are independent copies and are not erased by local deletion.

Schema-13 and older engines must not open schema14. Use the original compatible backup at a separate path for rollback. The [synthetic compatibility receipt](evidence/private-task-schema-compatibility-2026-09-22.json) verifies preservation from the actual prepared PR104 schema12 engine, refusal by that older engine, and separate restoration of its original backup. Reproduce after building with the reviewed `BITTREES_OLD_APP_RESOURCES` and `scripts/check-private-peer-upgrade.mjs`. The tests additionally exercise schema13→14 migration. This is disposable-store evidence, not a personal upgrade or native acceptance.

## Verification and remaining work

Tests exercise actual HPKE messages through reviewed keys into the ordinary queue and synthetic worker, exact duplicate/concurrent delivery, conflicting encrypted retries, restart, current consent and revocation, payload authority injection, wrong sender/routes/epochs, transactional failure, capacity, owner isolation, encrypted backup restore, schema migration and authenticated export/deletion. No personal database, Keychain item, installed app, model setting, hosting service or Acer-server process is changed.

Still open: persisted endpoint keys and user-held recovery, reciprocal enrollment/UI, durable sender outbox, actual consent and startup wiring, encrypted conversation replies/results/exact approvals, offline/reconnect UX, live transport and retention decision, independent protocol review, native/browser acceptance and signed client/update trust. Relay ciphertext retention and operational-metadata retention remain unanswered separate questions; this local-only module sets neither policy.
