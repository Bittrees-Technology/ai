# First-time native owner pairing

This is inactive client preparation. No launcher, HTTP route, dashboard, model or MCP tool imports these modules. The reserved Roles start/poll paths are a proposed counterpart contract, not deployed endpoint evidence. Shipping these modules does not activate pairing.

## Boundary

An existing local Ed25519 identity and explicit native consent start pairing. There is no existing Roles bearer, credential, owner/profile UUID, workspace, native lease or Agent controller prerequisite. Roles derives the owner later from its original authenticated session, with current active-person identity and applicable Roles. Registration and pairing grant no action authority.

`initial-pairing.ts` creates a dedicated signed initial request and fresh signed polls, verifies a short-lived Roles-signed metadata result, binds the exact request/challenge/poll/native consent, and caps consent at five minutes and 62 calls. Unknown start outcomes remain held under their saved operation ID; reconstruction never automatically starts another mutation. Source results require `rolesCredentialId: null`, `runtimeEnrolled: false`, no workspace/lease/controller and no permissions. The key fingerprint is not a usable Roles credential. Pairing must not insert a generic MCP credential or activate a preexisting grant.

`initial-pairing-store.ts` supplies an encrypted SQLite journal using the already unlocked native Vault, identity-bound authenticated encryption, FULL/WAL durability and revision CAS. The caller owns the connection and must enforce its native owned-path/no-symlink/file-permission policy before opening it. Concurrent starts/polls cannot overwrite a newer durable result. Synthetic SQLite tests close and reopen the database and verify unknown-outcome retention without replay. These tests establish no production enrollment or persistence acceptance.

`initial-pairing-native-journal.ts` assembles that store with the existing owned-path guard. It requires a canonical absolute path, an operator-owned 0700 direct parent, safe ancestors and a single-link 0600 regular file; symlinks, hard links and hostile SQLite sidecars are rejected. A dedicated SQLite application ID/version and exact schema prevent opening another app's database. Only a newly created file is initialized, with its identity committed before WAL. Preexisting empty, foreign or damaged files remain held for operator reconciliation; they are never truncated, repaired or chmodded. The guard pins and checks the file around SQLite open and initialization; its documented trust assumption excludes a hostile process with the operator's full UID access. The supplied Vault must already be unlocked through the separate native approval. Construction creates no key, credential, source request or grant. The caller must close the returned journal when its native session ends.

`initial-pairing-https.ts` allows only the two exact HTTPS POST endpoints. It sends no credential, cookie or Origin header, forbids redirects, pins a validated public IPv4 address while retaining hostname TLS verification, caps responses at 16 KiB and requests at 15 seconds, and rechecks source/native admission after DNS and response completion. Its trusted admission callback must enforce exact native consent, reviewed source signing purpose and current source/cost evidence. No network occurs on construction. Responses cannot choose the trusted source key.

`initial-pairing-signer.ts` reads only the existing encrypted task identity and checks key continuity. It signs only canonical initial-pairing request/poll domains under current exact native consent. Missing keys do not initialize themselves. No private key is returned, no workspace is required, and neither wallet, transaction, delegation nor generic MCP signature domains are accepted. A future device-held transaction key must remain separate.

`initial-pairing-native-session.ts` composes those pieces for a future trusted native caller. Its constructor performs no disk, Vault, Keychain, DNS or socket I/O. Each explicit start/poll requires exact current native consent and a caller-provided source-purpose admission check bound to an independently reviewed Roles key fingerprint. The existing task identity is checked before opening the private journal; signing rechecks identity continuity. Requests always pass through the fixed HTTPS adapter and its before/after-DNS/response admission checks. Synthetic acceptance injects resolver/socket implementations only inside trusted test code; these are never model, environment or browser configuration.

The native caller must await `close()` when cancelling or ending the session. It aborts transport, drains the in-flight operation, then closes SQLite, retaining uncertain starts as held. Construction never resumes work and polling is not scheduled automatically. Another session cannot silently resend a held start. A successful metadata result still has no Roles credential, runtime enrollment, workspace, lease, controller or action permissions. The session remains unregistered in all running surfaces; a source-admission callback is an integration prerequisite, not evidence that the current source purpose, signing key or account/cost checks have been approved.

`initial-pairing-native-review.ts` prepares the exact scope for a future native confirmation handler. It binds the inspected public principal/key fingerprint, independently reviewed Roles key fingerprint, fixed endpoints, metadata-only purpose and original five-minute expiry into a dedicated review digest. It supplies no owner ID: Roles must derive the owner from its authenticated active person and current applicable role. Preparing a review performs no identity inspection, source admission, session construction or network action. Native approval accepts only the current review ID and exact digest, consumes confirmation before source admission/session creation, and cannot renew expiry or expand permissions. Cancellation clears consent and rejects late results; an uncertain start cannot reuse the consumed confirmation. Clock rollback cannot extend the review beyond five minutes. This module is unregistered: no native UI or helper currently calls it, and its unit acceptance does not prove a human confirmation or source authorization.

Before starting, the review controller also compares the session's public `reviewBinding()` against the exact reviewed local principal, local key fingerprint and Roles key fingerprint. A factory accidentally wired to another source key is closed before signing or transport; the review digest cannot approve one key while the session uses another. The binding getter performs no I/O and returns no credential or private material.

The review now also binds the enforced ceiling of 62 requests, 300 seconds and $0 additional spending. Request/duration constants are shared with the pairing state machine; the actual session binding must match these limits before start. The zero spending field is a limit requiring current source/cost admission, not evidence that a source API is free.

`apps/macos/InitialPairingReview.swift` independently validates the Node review before a future native confirmation display. It requires separately remembered native identity and reviewed source-key fingerprints, the exact envelope/fields/endpoints/purpose/limits, genuine JSON booleans, safe integer timestamps and the same domain-separated canonical digest. Confirmation construction rechecks expiry/clock rollback and returns only review ID/digest, never editable scope. A human-readable summary includes identity/key bindings, endpoints, original expiry and request/spending limits. The cross-runtime fixture covers the actual Node-produced review plus tampered or re-hashed scope/type/limit proposals. Package/typecheck lists include this file, but no window, menu or helper currently calls it. These tests do not constitute native human approval, source admission or installed activation.

## Required counterpart and native wiring

Before activation, the Roles owner must implement/review actual start, fresh-session owner review and poll routes; current person/role/source-purpose checks; durable replay/rate/expiry controls; atomic cross-owner/no-resurrection binding; and a reviewed source verification key specifically admitted for this metadata purpose. Existing runtime-enrollment source keys are not automatically approved for this new purpose.

The native owner flow must provide real bounded consent, safe owned journal open, existing-key signer and fixed transport with exact admission. Inspection/local initialization remains a separate explicit action. Do not synthesize IDs or flags, expose the helper to the model/browser, accept pasted private keys, or direct the user to an unimplemented source endpoint. Cancellation during the durable result write leaves the outcome held.

Actual runtime credential/device enrollment, canonical Agent controller admission, per-action Roles/source scope, until-revoked delegation, central worker execution and successor/revocation evidence remain separate acceptance requirements. No Safe or other transaction approval is implied by pairing.

## Prepared native confirmation sheet

`InitialPairingUI.swift` supplies a native-only sheet presenter for the future trusted helper. It is compiled but not called by a menu, helper, HTTP route, browser or model. It accepts a proposal only with separately remembered current native identity and reviewed Roles source-key bindings. Cancel is the default keyboard action; pairing requires the second button. The sheet consumes either approval or cancellation once, rechecks the original expiry and current bindings at confirmation, and cancels on application focus loss, parent window closure, unavailable/changed bindings, expiry or clock rollback. A common-mode timer checks the open review every 250 ms. Ending a sheet clears handlers before callbacks to prevent duplicate completion. The trusted native owner must retain the presenter and call cancel during shutdown.

The presenter returns only review ID/digest, never source requests, keys or permissions. The source-purpose/cost admission checks in the review controller and session still run separately before any actual request. Pure confirmation-gate tests cover cancel/replay/context loss/expiry/no revival; compiler checks cover the AppKit presenter. These do not establish actual human interaction or installed native acceptance. Runtime wiring remains held until the Roles counterpart and trusted native helper supply real source admission and independently remembered bindings.
