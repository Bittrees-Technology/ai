# Browser task relay transfer

The verified BrowserKeyHost now exposes separate explicit `relayTaskAPI.prepare` and `relayTaskAPI.send` operations. Existing local task preparation/handoff remains available. Neither API starts a scheduler, selects a model, changes task permission, registers a device or enables a relay grant. The visible task panel is not wired to these new operations yet.

The internal BrowserRelayTransport requires an active verified browser device scope plus the same current owner/session. It inspects the current independent browser relay permission, verifies its exact binding and expiry, and gives one bounded callback an ephemeral client. Scope change, invalidation, expiry, clock rollback and callback exit close that client. HttpOnly browser credentials remain outside JavaScript; no status or native relay secret is accepted.

The new endpoint-authenticated `/browser/relay/messages/recipient` and `/device/relay/messages/recipient` routes read the currently active opposite endpoint's relay identity. They verify the exact sender permission header and both endpoint/grant states under the existing authority transaction. Readiness is advisory and never grants decryption/task authority. Submission repeats current permission checks in its own transaction. The routes are absent without the existing explicit complete private policy.

Preparing a task for relay caps its reviewed encrypted-envelope deadline to the task consent, sending connection and receiving connection deadlines. Confirmation still consumes the original exact-content review and durably reserves/seals one outbox entry. Sending checks current relay permissions before taking that retained envelope through fresh task/peer/key/consent checks. It does not reseal or allocate another task on retry. An entry prepared for a longer delivery window than current relay permissions is rejected rather than silently rewritten.

The send result is marked `transportOnly: true` and contains the bounded verified storage receipt. It cannot mark a browser task accepted or completed: only the existing authenticated endpoint receipt/result path can do that. Lost replies can be retried deliberately after reading the current local entry revision; the same message/envelope reaches the relay's exact duplicate/tombstone handling. No automatic retry is introduced. A scope change suppresses late responses, but a message already handed to the transport cannot be recalled.

Seven new engine cases cover recipient response binding and the browser scoped bridge. The actual full HTTPS/PostgreSQL integration covers pending/active/revoked recipient permissions, cross-owner denial, exact sender permission headers, separate credential scope and both transport directions. The test browser adapter now adds only browser-provided Origin/fetch-site/cookie headers, preserving the actual client's account and permission headers.

Three actual-browser scenarios (nine cases across Chromium/Firefox/WebKit) are authored for real HTTPS/SIWE/HttpOnly registration plus retained IndexedDB and independent synthetic Mac SQLite/key stores. They cover capped preparation, exact encrypted transfer and reopen, response loss/duplicate retry, task admission deduplication and cancellation during recipient inspection. Those cases have been built and typechecked but have not run yet; disposable GitHub CI is required. All644 local engine tests, typecheck, production/fixture build, contracts and full synthetic HTTPS/PostgreSQL pass.
