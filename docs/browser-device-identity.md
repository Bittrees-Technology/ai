# Verified browser registration and key authority

Status: internal service/client integration, exercised through synthetic PostgreSQL, HTTPS and disposable browser fixtures. The [signed-in page](production-browser-recovery.md) now mounts its reviewed registration and key-recovery controls; no live migration or private access is activated by repository integration. It provides a browser's own verified identity; it does not reuse a Mac's status-publishing credential. Acer news/model jobs and Mac inference remain independent.

## Explicit registration

Migration 008 adds `remote_browser_devices`, separate from companion devices, sessions, keys and ciphertext. An explicit `POST /browser/registration/create` requires a current SIWE session, the displayed account header, an operation UUID, exact reviewed prior device/epoch (or null) and `confirmed:true`. The server allocates a random device UUID, epoch 1 and a random 256-bit cookie secret. The secret is stored only as a domain-separated SHA-256 hash and delivered only in a `__Host-` Secure/HttpOnly/SameSite=Strict/Path=/ cookie. JSON responses contain identity and session expiry, never the cookie secret or any key.

The browser lease uses the existing configured device lifetime (one minute to thirty days). It is independent of the sign-in session: logout stops verification immediately at the service, while a later explicit sign-in to the same account can use the retained unexpired browser registration. Neither sign-in nor inspection extends its lease. A different account cannot inspect, use or revoke it. Replacing the current cookie's reviewed registration retires that row and advances its epoch in the same transaction as the new insertion. Unknown/other-owner cookies reveal no registration. Two first registrations without a cookie can represent separate browsers; there is no hardware fingerprinting or silent device identity inference.

Each owner has a bounded lifetime registration count (default 100, using the existing configured device quota). Revoked/expired rows count toward that limit; no automatic history deletion or policy for relay content is introduced. Owner-scoped listing returns at most 50 rows per page. Explicit epoch-bound revocation works from another authenticated browser and does not claim to delete keys, ciphertext, source grants or exported backups.

Creation operation IDs cannot be replayed, including after losing the response. Inspect explicitly to reconcile a cookie already accepted by the browser; otherwise review a fresh replacement. There is no automatic creation retry or recreation of an old ID. A missing creation acknowledgment does not become proof of fresh registration merely because inspection returns a valid identity.

## Verification and transaction boundaries

`inspect` reports current cookie metadata, including expired/revoked history, under a verified matching owner session. `identity` requires both that session and a live, unrevoked browser cookie. `list` and `revoke` use the owner session and never trust an owner in the request body. Browser routes retain exact direct TLS/host/origin, same-origin fetch/CSRF header, no bearer authorization, bounded JSON, rate limiting and no-store responses. Device bearer routes reject browser cookies; browser secrets cannot authenticate companion status or a sign-in session.

The session row and registration are checked under the same PostgreSQL transaction. Shared session/identity locks serialize against logout and revocation. Replacement also holds an owner-specific capacity lock and the prior registration row; stale epochs and duplicate operation IDs fail. Commit-time session/registration expiry or clock rollback rolls back mutations. The new table stores only registration metadata and a cookie hash. It has no source permission, task, private-key or content columns.

## Bounded browser client

`BrowserDeviceClient` sends explicit same-origin requests to the fixed ai.bittrees.org endpoint, without reading or supplying cookie secrets. Responses have bounded streaming reads and strict schemas; errors expose only fixed status codes. The trusted host supplies the displayed owner and a session-scope identifier, and must call `invalidate()` immediately on logout, lock or scope changes, even if the next account is identical.

`withVerifiedDevice(expectedBinding, action)` verifies the exact reviewed binding at the service, then supplies `current()` only during a maximum 30-second operation. The deadline includes network time and is capped by both the session and registration lease; wall and monotonic clocks are checked. Each callback must check that scope at its own final commit alongside separate peer and operation permission checks. The client verifies the cookie identity again before releasing the callback's result, and permanently invalidates the scope at return/failure. Requests serialize per instance; the host must coordinate its managed client, other tabs and account changes.

Revalidation can suppress a result after revocation or a cookie change; it cannot undo an operation already committed during the bounded verified interval. This is not instantaneous remote revocation, a live subscription or an offline grant. There is no automatic retry, credential renewal, cached positive scope or plaintext fallback.

An explicit acknowledged registration is followed by another identity check to prove the cookie was accepted. Only that observation in the same client instance can supply the lifecycle's `freshRegistration` callback, and only for two minutes, bounded by both leases. Ordinary inspection, sign-in, reload, recovered key material and a new client instance cannot manufacture that proof. If the observation is lost before initial setup, explicitly review replacement registration. Existing initialized keys require current verified identity but do not require a new fresh-registration claim on every use.

## Evidence and release work

Unit checks cover strict identity matching, malformed/oversized responses, fixed error codes, missing cookie acknowledgement, session/device expiry, wall/monotonic bounds, invalidation, account/session changes, overlap, callback failures and post-operation revocation. Real PostgreSQL tests cover signed sessions, hashed secrets, cross-owner/credential separation, replay, quota, replacement concurrency, observed revocation/logout lock waits, rollback and independent lease expiry. Real HTTPS tests exercise the shipped client against actual routes with synthetic cookie transport.

The disposable browser suite additionally uses a closed loopback CONNECT proxy that accepts only the synthetic ai.bittrees.org target and connects directly to the fixture HTTPS server. It never resolves or connects to the public host. Requests and cookies pass through each browser’s actual network stack to the real service and isolated PostgreSQL schema; there is no request interception or cookie injection. The isolated context accepts its fixture-only self-signed TLS certificate, so this does not claim production certificate trust acceptance. Actual browser-managed Secure/HttpOnly cookies, the shipped client, IndexedDB lifecycle and WebCrypto setup are exercised together in Chromium/Firefox/WebKit. No request reaches the public ai.bittrees.org service. Browser checks cover reload, same-owner re-login, account isolation, competing tabs, delayed-response invalidation, revocation during a callback and expired registration. They do not claim real wallet-extension, personal Safari/WKWebView or live deployment acceptance.

Production registration/revocation UI and verified-host mounting are now integrated in the [signed-in page](production-browser-recovery.md). Reviewed historical-key recovery/rotation, automatic lease renewal, reciprocal pairing, encrypted transport, independent cryptographic review and personal acceptance remain unfinished. The installed app, prepared archive and all Mac/browser-content schemas are unchanged. This adds server migration 008 only; it is not applied to a live service. Relay retention remains an unresolved separate decision.
